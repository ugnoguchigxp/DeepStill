# 逐次キューと回答価値に基づくラウンド探索の実装計画

更新日: 2026-09-12。版: 2。状態: v2実装・固定経路検証済み。実装時の具体化と未実測項目は[実装記録](round-research-implementation.md)、採点と改訂理由は[計画レビュー](round-research-review.md)を参照。以下は採点時の設計を保持する。

[設計資料一覧](README.md) / [既存の実装計画](plan.md) / [品質設計](report-quality-design.md)

## 1. 目的と判断基準

ユーザーに十分な情報を提供できるかを、取得済みの根拠に基づいてLLMが評価する。そのうえで、残予算に余裕があり、理解を深める候補があれば探索を続ける。少ないラウンドで終了すること、検索数を減らすこと、予算を使い切ることのいずれも単独の成功条件にしない。

中心となる回答の充足と、補足による価値向上を別々に判定する。補足には具体例、仕組みの説明、歴史的背景、意外な関係、誤解しやすい点、出典で確認できるトリビアを含む。関連語があるだけの横展開は採用せず、「この情報があると読者の理解がどう変わるか」を説明できる候補を選ぶ。

ユーザーの指定条件・除外条件は維持する。たとえば比較対象から除外された方式を、トリビアという名目で推奨候補へ戻さない。範囲内の説明を豊かにすることと、調査テーマを拡大することを区別する。

## 2. 現状と変更点

2026-09-12時点のローカルコードを確認した。以下はコード上の挙動であり、live実測結果ではない。

| 現状 | 変更する挙動 |
| --- | --- |
| Workerは `await engine.tick()` で逐次実行 | 維持し、複数調査や誤った二重起動でも探索実行枠を全体で1にする |
| `seed → suggest` で最初に複数クエリを生成 | 初回はテーマを起点とする1クエリで一次探索。派生クエリは読解後の評価で選ぶ |

| 読解時のconceptsを直ちにQueryへ追加 | 候補として記録するだけにし、全選出資料の処理後にまとめて評価 |
| 新規Claim増分と `lowGain >= 2 && round >= 3` で飽和停止 | 回答十分性・追加価値・予算を使う判断へ置換。増分は補助指標として残す |

| tasksはjob_id UNIQUEで、調査ごとに1つの制御タスク | 制御タスクを維持し、個別作業用の永続キューを新設 |

## 3. ラウンドの定義と流れ

1ラウンドは「確定した検索計画を実行 → 候補資料を選出 → 選出資料を全件処理 → 中間評価」までとする。初回も1ラウンドとして数える。検索クエリ1件やURL1件をラウンドとして数えない。

1. ユーザーの原文と既存researchBriefから、回答すべき点と明示条件を保存する。初回検索はテーマそのもの、または意味を広げず検索可能な長さに整えた1クエリに限定する。
2. ラウンドに採用済みの検索クエリを一件ずつ実行する。初回に多言語・派生語を大量に列挙しない。
3. 検索結果のID、タイトル、概要、出典、既取得状態をLLMに渡す。読む資料、目的、優先度、見送り理由を構造化出力させる。
4. 選出した資料を一件ずつ取得・読解する。資料ごとの疑問やキーワードは候補として保存するが、次ラウンドの検索は開始しない。
5. 選出資料がすべて読解完了または理由付きの処理終了になったら、中間評価を一度確定する。評価では全ラウンドの蓄積と今回の追加分を参照する。
6. 不足を埋める探索、価値を加える探索、回答統合のいずれへ進むか決める。次の検索クエリと読む目的はこの時点でLLMが選出する。

「全件処理」は無制限の再試行を意味しない。取得不能、抽出不正、関連本文なし等は理由付きで記録し、読解成功と区別して評価する。本文の一部だけを読んだ資料は、読解範囲と切り詰めを記録し、全文確認済みとは扱わない。予算切れで未処理が残る場合は通常のラウンド完了にせず、中断状態と未読資料を評価へ渡す。

検索結果が空の場合も「検索成功・候補なし」として評価へ進む。通信失敗、応答不正、未完了pollとは区別する。

## 4. LLM評価の契約

### 4.1 回答の十分性

`RoundEvaluation` は少なくとも以下を保存する。

| 項目 | 内容 |
| --- | --- |
| requirements | ユーザーが求める回答項目と明示条件。途中の資料に合わせて要件を消さない |
| coverage | 回答項目ごとの sufficient / partial / missing、理由、根拠Claim ID |
| materialGaps | 結論・理解に影響する不足と、解消した場合の価値 |
| contradictions | 残る対立、適用条件の違い、回答に必要な留保 |
| answerOutline | 現在の根拠で書ける説明の骨子と支持Claim ID。最終文章の品質保証とは分ける |
| sufficient | 中心の問いへ根拠付きで答えられるか。説明可能な不確実性も明示する |
| opportunities | 追加探索候補、目的、期待価値、既存内容との差分、候補キーワード、順位 |
| recommendation | fill_gap / enrich / finalize、および理由 |

総合点だけで十分性を決めない。重要な回答項目が欠けたまま、周辺情報の多さや流暢さで「十分」にしない。引用が実在しても主張を意味的に支持するとは限らないため、根拠と適用条件の対応も評価する。

LLMには原文、回答項目、根拠付き要約、矛盾、失敗、候補履歴、残予算を渡す。大きな本文を毎回全投入せず、資料別の読解結果から評価用の証拠一覧を作る。上限を超える場合は一件ずつ圧縮してから評価し、参照ID・反証・欠落情報を保持する。必要な証拠を入力に収められなかった評価は十分と確定しない。

### 4.2 追加価値の選出

候補には `purpose: core | supplement | trivia`、答えたい小問、読者への効果、関連Claim ID、未確認の仮説、想定する出典、期待価値、推定コストを持たせる。LLMは候補を比較して順位を返す。コスト推定は実績からプログラムが補正し、LLMの自己申告だけに依存しない。

補足の価値は、理解の深化、具体性、既存本文との非重複、テーマとの関係、確認可能性で評価する。単に珍しい、単語が近い、検索しやすいという理由では採用しない。探索前のトリビア候補は仮説であり、出力に採用するには本文根拠の確認が必要。

既に不足解消済みの小問、失敗続きの候補、以前見送った候補を再提案する場合は、新しい根拠や条件の変化を必須にする。小さな言い換えで同じ検索を反復しない。

### 4.3 継続の判断

| 評価と予算 | 次の行動 |
| --- | --- |
| 中心回答が不足、実行可能で価値のある不足解消候補あり | fill_gap。重要な不足を先に選ぶ |
| 中心回答が十分、残ラウンドと実行予算に余裕、価値ある候補あり | enrich。補足・トリビアの候補を上位から採用する |
| 中心回答が十分、予算が少ない | 小さく完遂できる高価値候補だけを検討し、成立しなければ統合 |
| 中心回答が十分、有望な候補なし | 予算が残っていても統合 |
| 中心回答が不足、実行可能な有望候補なし、または予算上限 | 部分回答として統合し、何が答えられないか明示 |

中心回答が不足しており不足解消の経路が尽きた場合でも、有望な補足候補と十分な予算があれば、`sufficient=false` を保持したままenrichへ進める。欠落を補足で埋めたことにはせず、最終出力は部分回答とする。これは上表の「有望候補なし」に該当しない。

ラウンド数が少ないことをLLMへの評価報酬にしない。十分になった直後もopportunitiesを評価し、有望候補と余裕があるのに終了する場合は、その見送り理由を記録する。一方、余った予算を消化するためだけの候補生成はしない。

## 5. 予算

既存Budgetに `rounds` を追加する。初期の調整可能な設定案は最大6ラウンド、1ラウンドあたり検索最大2件・選出資料最大4件とする。初回検索は1件。これらは性能の実証値ではなく、比較検証で調整する開始値である。

残ラウンドは「上限 − 開始済みラウンド数」で求める。再起動やpoll、同じラウンドの再開では加算しない。「余裕が多い」の初期条件は残ラウンド2以上に加え、次ラウンドの検索・取得・読解・評価を完了でき、最終統合の予約も残せることとする。残り1ラウンドでも有望な小規模探索は許可する。

tokens、requests、costUsd、urls、documents、wallMs等の既存上限はすべて有効。ラウンドが残っていても他の予算が足りなければ開始しない。LLMの選別・scope・評価・圧縮も使用量へ計上する。統合と必要な品質確認の予算を先に確保し、探索が使い切らないようにする。予約量はプロンプト上限と実績に基づき、推定超過は記録する。

既存のusage不明・結果不明の扱いを維持する。料金や使用量が不明な外部処理を無条件に再送しない。ラウンド上限と探索深度は別制約として扱う。

## 6. 永続キューと実行制御

既存tasksを調査の制御・停止・再開用に残し、新migrationで `research_work_items` を追加する。適用済み0001.sqlを書き換えない。ラウンド、評価、候補の詳細は既存recordsに保存し、UIに独立した正規状態を持たせない。

作業項目はid、jobId、roundId、kind、purpose、payload、status、priority、priorityReason、dependsOn、nextAt、attempts、operationKey、revisionを持つ。kindはsearch_submit / search_poll / select_sources / fetch / read / evaluate / synthesize等とする。状態はpending / running / succeeded / failed / skipped / cancelledを区別する。

依存関係と実行可能時刻を満たす項目から、ユーザー指定優先度、LLMの順位、登録順で次の一件を決める。同点では決定的な順序を使う。調査をまたいだ待ち過ぎを防ぐため、同優先度の調査間では順番を回す。LLMの評価と安全な実行可否は分け、プログラムが未充足の依存を飛び越えないようにする。

自動の検索追加はラウンド評価後だけにする。実行途中のユーザー指示は永続化し、未開始項目の優先変更を次の選択に反映する。新しい探索目的は次ラウンド候補として保存する。原依頼の範囲変更は別Jobとして開始する。実行中項目の通常の優先変更では中断せず、停止・取消はAbortSignalを使う。

ワーカー全体の実行枠を1つにし、検索・読解・評価・統合を競合実行しない。単一プロセス内のasyncはAPI応答や待機のために使い、探索並列化には使わない。別起動したworkerやCLIが迂回できない共通の排他制御を設ける。既存の調査スクリプトによる直接LLM呼出しもこの枠を使う。

所有権喪失時は中断し、新ownerは旧処理が止まったと確認できない外部要求を重ねない。特に外部LLMは通信切断だけでは推論停止を保証できないため、結果不明の状態を維持する。DataForSEOのsubmit/pollでは未完了検索を保持し、同時に新しい検索をsubmitしない。検索プロバイダー内に複数探索を隠さない契約を追加する。CodexSearch内部の探索回数を確実に制御できない場合、その経路を厳密逐次対応とは扱わず、LocalLLMと単発検索Adapterの経路で保証する。

結果保存、作業完了、後続項目登録は既存leaseを確認する同一トランザクションで確定する。評価の保存と次ラウンド作成も原子的に行い、再開時の二重ラウンドを防ぐ。外部API呼出しとDB保存を同一の原子操作とみなさず、既存operation記録で結果不明を扱う。

## 7. 出力と進捗

レポートでは中心回答を先に示し、その理解を深める補足を自然な位置に組み込む。独立して読む価値があるトリビアは短い補足欄にできるが、固定の件数や文字数を埋めるためには追加しない。補足にも中心回答と同じ引用・条件確認を適用する。

候補の期待価値と、実際に本文へ採用された価値を分けて保存する。期待外れだった探索は成果として水増ししない。enrichの結果、中心回答を覆す根拠が見つかった場合は十分性を再評価してfill_gapへ戻す。

進捗にはラウンド番号、目的（不足解消／補足）、選出資料の処理数、現在の一件、回答十分性、次へ進む理由、残予算を表示する。「回答に必要な根拠は揃い、補足を調査中」の状態を表現する。イベントはDBへ保存し、SSEとリロード後の画面は同じ状態から再構成する。

探索の十分性評価と、生成した文章の品質レビューは分ける。十分な根拠があっても生成物の説明不足は起こるため、最終レビューで本文・根拠対応・補足の有用性を検証する。中心回答が十分で補足だけ未完了なら、それだけを理由に回答全体をpartialにしない。

LLM応答はZodで検証する。未知の資料ID・Claim ID、重複ID、選出上限超過、不足項目の説明なしでの十分判定などを拒否する。不正評価で次ラウンドや十分判定を確定しない。安全に再試行できる確定済み不正応答のみ上限付きで再評価し、解消しなければ評価不能として停止または根拠付き部分出力へ進む。

旧JobにはengineVersionを付けて既存経路で停止・再開できるようにし、新Jobだけを新経路へ切り替える。進行中のhits/indexを暗黙に新ラウンドへ移さない。新しいrecords・テーブルは追加方式とし、ロールバック時も削除しない。API拡張はJob予算、探索状態取得、待機項目更新に限定し、認証方式や外部サービス登録は変更しない。

## 9. 検証と受け入れ条件

資格情報不要の固定providerで、以下を再現する。内部関数の呼出し回数だけでなく、保存状態、実際の開始順序、出力の根拠を確認する。

- 一次探索前に派生クエリを一括生成しない。次のクエリは選出資料の全件処理後に決まる。
- 検索rank最上位とLLM選出が異なるfixtureで、LLMの理由と選出が実行へ反映される。
- 全資料の処理途中では評価・次ラウンド検索が始まらず、失敗資料を読解済み根拠に含めない。
- 不十分なら重要な不足を先に探索する。十分でも残予算と有望な補足候補があれば継続し、出典付き補足が成果物に入る。
- 十分かつ有望候補なしなら予算を残して終える。不十分かつ予算なしなら、十分と偽らず部分回答する。
- 残ラウンドが多くてもtoken等が足りなければ開始しない。最終統合用の予約を探索に流用しない。
- 新規Claim数が増えなくても、重要な裏付け・反証で理解が改善した場合は価値として評価する。
- 補足で中心回答が覆った場合は十分性を撤回する。根拠なしのトリビア、除外条件違反、同じ内容の言い換えは採用しない。
- 管理対象の複数Job、二重worker、CLI併用でも実行枠は1。再起動や評価直後のcrashで同じ後続作業を重複登録せず、送信結果不明時には自動再送を拒否する。外部側でのexactly-onceを保証したとはみなさない。
- 優先変更は次の未開始作業へ反映し、API更新との競合で変更が消えない。停止・再開後も同じラウンドと既読資料を保持する。

比較テーマには、単純な事実、仕組みの説明、明示条件付き比較、見解が対立する問い、資料不足、価値ある補足が存在する問いを含める。変更前後で同じテーマ・資料fixture・予算・モデル設定を使う。

主指標は回答項目の充足、根拠の妥当性、説明の深さ、補足の有用性と非重複、範囲遵守とする。検索数、ラウンド数、時間、tokens、見送り率、採用補足あたりの追加費用は副指標として併記する。短時間で終わっただけでは合格にせず、ラウンドが増えても説明価値が改善した場合は評価する。

同じLLMの自己評価だけで品質改善を結論づけない。固定の期待分岐と引用検証に加え、順序を伏せた人間の比較レビューで主要回答と補足の価値を確認する。live検証ではprovider内部の検索回数と実usageも記録し、fixtureの成功をLocalLLM実機性能の証明にしない。

## 10. 採用しない案とトレードオフ

最初に大量の検索クエリを生成する方式は、一次探索の学びを反映しにくいため採用しない。資料一件ごとに次の検索を開始する方式は、選出全件を読んでから評価する要件と合わない。十分判定で即終了する方式は補足価値を取りこぼし、全ラウンド消化を必須にする方式は不要な探索を増やす。

ラウンド境界の評価は、資料一件ごとの再計画より反応が遅い。その代わり評価呼出しを抑え、複数資料の比較を踏まえて判断できる。選出件数を制限し、ユーザーの停止・優先変更は随時受け付ける。逐次実行による所要時間の増加は許容し、LocalLLMの安定稼働と結果の価値を優先する。

今回の実装対象は逐次探索・判断・保存・表示・出力の変更。分散ワーカー、新しい検索サービスの契約、LocalLLMのモデル選定や配備、認証変更、ContextStillへの自動登録は対象外とする。

## 11. 実装契約の具体化

本節はレビューで明確化した契約であり、前節の概略を具体化する。設定値は開始時にJobへ保存し、途中でデフォルトが変わっても既存Jobへ適用しない。

### 11.1 回答項目と候補の採用条件

初回検索前に `prepare_brief` を1回実行する。原文から回答項目を抽出するだけで、派生検索は生成しない。回答項目にはID、原文の対応箇所、required / optional、何を説明できれば充足するかを保存する。テーマのみの依頼では、LLMが想定した説明項目を「推定」として明示し、ユーザーの明示要件と区別する。ユーザーの変更以外でrequiredを消去・optional化しない。

十分性は、requiredの全件に有効なcoverageがあり、重要な欠落や未説明の対立がなく、証拠一覧の入力欠落がない場合だけ許容する。未確定な事柄については「未確定であることを根拠とともに説明できる」場合を充足にできるが、単なる取得失敗をその証明にしない。プログラムは全IDの網羅と参照整合を検査し、意味の妥当性はLLMと品質レビューで検査する。

追加候補はLLMが以下の各軸を0〜2で評価し、根拠を記す。0は満たさない、1は限定的、2は具体的な改善を説明できる状態とする。

| 軸 | 2の判定例 |
| --- | --- |
| 読者への価値 | 特定の仕組み、誤解、比較条件を具体的に説明できる見込み |
| 追加性 | 既存の説明にはない具体例・反証・関係を加えられる |
| 確認可能性 | 検証したい事実と、探索する原典の種類を特定できる |

明示条件への適合とテーマとの説明可能な関係を必須条件とし、各軸1以上・合計5以上を有望候補の初期基準とする。これは探索前の期待評価であり、事実の信頼度ではない。実行可能な有望候補はLLMの順位で採用し、余裕が少ない場合は上限内で完遂可能な最上位候補1件までに絞る。人間の優先指定も予算や明示除外を無効化しない。

同一候補は正規化クエリ、回答項目ID、探索目的で識別する。言い換え候補はLLMが履歴の小問と比較して重複理由を返す。未採用候補は次回評価へ持ち越し、登録上限はJobあたり50件とする。超過分はキューに積まず理由をイベントへ残す。上限値変更は戦略versionを更新する。

### 11.2 状態遷移と全件処理の条件

| Roundの状態 | 次状態へ進む条件 |
| --- | --- |
| planned | 予算の確保と開始回数加算を原子的に確定してsearching |
| searching | 採用済み全検索が確定したらselecting。結果不明はblocked |
| selecting | 全候補へのLLMの選出・見送り判断を保存し、選出集合を固定してreading |
| reading | 固定集合の各資料がread完了または理由付き終端になればevaluating |
| evaluating | 同じ計画revisionの評価を保存し、evaluatedへ。次Roundはこの後にのみ作成 |
| interrupted | 予算・範囲変更等で未処理集合を保存。予約が許せば中断評価、なければ既存根拠を出力 |
| blocked | 外部処理が結果不明。新たなprovider要求を停止し、解消確認後に元の状態へ |

停止はJobの既存cancel/resumeで扱い、Roundの進行位置を保持する。cancelledの作業項目はユーザーによる恒久取消を表す。単なる停止で未開始項目をすべてcancelledにはしない。

検索候補が多い場合は8件ずつLLMで予備選別し、最後に残った候補を比較して最大4件へ確定する。予備選別は逐次実行し、バッチ間の見落としを評価ログに残す。選別コストはラウンド見積りに含める。選出0件も明示結果として評価へ進む。既存snapshotが使えるURLは取得を再利用するが、以前の読解範囲で今回の小問に答えられなければ追加読解を積む。

fetch成功だけでは全件処理の条件を満たさない。fetch失敗時は依存するreadを理由付きskippedへ進め、失敗資料IDを評価に含める。selectedSetVersionを固定し、全件処理の確認とevaluate作成は同一トランザクションで行う。新しい資料を途中で自動補充せず、次ラウンド候補にする。

### 11.3 予算予約と不足時の出力

使用済み量と未使用の予約を分け、判断可能残量を `上限 − 精算済み使用量 − 有効な予約` とする。既存reserveがusageへ加算する方式との二重計上を避けるため、新経路にはreservationレコードを設け、旧経路は既存台帳のまま扱う。予約→実績への振替と返却はoperationKeyごとに一度だけ行う。usage不明では予約を確定使用量として保持し、過小計上しない。

Job開始時に統合1回・レビュー1回・改稿1回・再レビュー1回の最大入力/出力に基づく予約を確保する。通常Round開始時は検索、選別、読解、圧縮、中間評価1回、不正応答の修正1回までを見積もって予約し、その範囲でのみ作業を追加する。実績が少ない場合は設定済みの上限値を使用する。資料件数を減らして成立するなら、その小さいRound案を採用する。

時間は金額のような厳密予約ができないため、`explorationDeadline = job.deadline − finishAllowanceMs` を設ける。finishAllowanceMsはproviderごとのタイムアウト上限と予定する最終呼出し数から計算する。残時間が初めから足りなければLLM探索を開始しない。deadline到達後はLLM評価も統合も開始せず、最後の確定評価と検証済みClaimから決定的に根拠一覧・回答可能範囲・不足を出力する。確定評価がなければ十分性はunknownとする。

不正な構造化応答の修正は同一入力につき追加1回まで、追加予約の範囲内で行う。通信結果不明の再送とは分ける。最後まで評価できない場合は `evaluation_unavailable`、予算不足は `budget_exhausted`、有望候補なしは `no_valuable_candidate` を理由として保存する。

### 11.4 単一実行と障害復旧

管理対象は一つのDeepStillローカル設置とその設定済みDBとする。無関係なアプリや別DBから同じLLMサーバーへの呼出しまでは保証しない。APIとCLIは実行要求をDBへ登録するだけにし、provider呼出しはworkerに集約する。旧Jobの再開、レビュー、改稿も同じworkerを通す。

追加テーブル `execution_slot` に固定ID、ownerToken、leaseUntil、operationKey、state（idle / active / blocked）、externalIdを保存する。取得はSQLiteの書込みトランザクションで行い、global slot→制御task→work itemを同時に確保する。commitは全tokenとrevisionを検査する。work itemにはownerTokenを保存し、operationKeyにUNIQUE制約、jobId/roundId/status/nextAt/priorityに索引を設ける。依存は同じJobの先行項目だけを許可し、循環・未知IDを登録時に拒否する。

送信前にoperationをpreparedとして記録し、送信開始時にin_flightへ遷移する。in_flightのままownerを失った場合、lease期限だけで枠を解放せずblockedにする。外部側の完了・取消確認またはオペレーターによる外部処理終了の明示確認で解放し、確認方法と操作者をイベントへ記録する。確認できなければ読み取りUIと停止操作だけを継続する。exactly-onceの外部実行を保証したと主張しない。

DataForSEOではexternalIdを保存できた場合のみ同じ要求のpollを復旧できる。未完了poll中はslotを保持し、新検索・LLM等の実処理を開始しない。これは時間効率より厳密逐次を優先する初期仕様である。ID保存前の不明POSTはblockedとする。Codexの不透明な内部探索は互換経路として明示し、厳密逐次の受け入れ試験から切り離す。

### 11.5 APIと計画revision

| API（追加予定） | 契約 |
| --- | --- |
| GET /api/jobs/:id/research | Round、待機項目、評価、予算予約、revisionをDBから返す |
| PATCH /api/jobs/:id/work-items/:itemId | expectedRevisionとpriorityを受け付ける。未開始項目のみ更新。競合・実行中は409 |
| POST /api/jobs/:id/exploration-candidates | idempotencyKey、expectedRevision、目的、小問を受け付け、次ラウンド候補として登録 |

新候補の登録はユーザーの依頼範囲を暗黙に変更しない。原依頼そのものの変更APIは初期実装から除外し、別Jobとして開始する。既存計画中の「範囲変更」はこの方法で扱う。候補と優先度の変更だけで本ラウンドの選出資料集合を増やさない。

評価入力にplanRevisionとevidenceRevisionを付ける。評価中に次ラウンド候補が追加された場合、根拠だけに依存するcoverageは再利用できるが、古いrecommendationでは次Roundを確定しない。追加候補だけを新revisionで逐次評価し、決定を保存する。連続更新時も最大1回の再判断とし、以降の更新は次境界へ持ち越す。受付revisionと反映予定RoundをAPI応答で返す。

### 11.6 互換性とリリース順

engineVersion未指定の既存Jobはv1と解釈し、roundsを遡及適用しない。新しいv2 Jobは必須のrounds・戦略version・予約情報を保存する。migrationは新テーブルを追加し、既存タスクのpayloadを変換しない。旧バイナリへ直接戻すとv2 Jobを誤処理するため、ロールバックは新バイナリ内のv2作成フラグを無効にする方式とする。v2の実行中Jobは停止・保持して修正版で再開する。

M1→M2→M3→M4の順にfeature flag下で実装する。M2完了前にCLIを新キューへ切り替えず、M4完了前に新規Jobの既定を変えない。M5でUIを接続し、M6通過後に既定化する。新ライブラリ追加や全体リファクタは予定しない。外部サービス変更など対象外の要求が発生した場合は、今回の計画へ暗黙に追加せず別途判断する。

## 12. 最終品質とリリース判定

### 12.1 最終レビュー失敗時

最終レビューの問題を「文章構成」「根拠不足・誤引用」「明示条件違反」に分類する。構成だけの問題は予約済みの改稿1回と再レビュー1回で修正する。根拠不足や条件違反も、保存済み根拠で修正可能な場合だけ同じ枠で直す。新しい検索が必要なら、本Jobの最終工程から探索へ無制限に戻らず、未解決点として残す。追加探索は完了済み評価が選んだラウンド内で行う。

修正後も中心の問いへの重大な問題が残る場合は `qualityState=needs_revision` とし、sufficientを確定済み根拠に照らしてfalseまたはunknownへ下げ、Jobをpartialとする。補足だけの裏付け不足なら該当部分を削除し、残りの引用・条件を再検査する。削除後も中心回答が十分ならcompletedにできる。文章の品質問題と回答の十分性を同じ一つの点数にまとめない。

レポート内の事実にはClaim/Evidence参照を必須にする。推論は前提Claimと推論であることを保持し、検索概要・未確認候補・LocalLLMの内部知識を事実の根拠に昇格させない。候補には最終採用段落IDまたは見送り理由を保存する。成果物の保存・export完了を確認してからJobを完了とし、export失敗は保存済み本文から再生成する。

### 12.3 比較評価の固定条件

M0で6種類のテーマ×2ケース、計12ケースの原依頼・fixture応答・期待回答項目・除外条件・期待補足を固定する。少なくとも4ケースは追加価値があり、2ケースは有望な補足がなく、2ケースは予算不足である条件を含む。モデル、プロンプトversion、設定、資料hash、使用量、全イベント、出力を `data/evaluations/round-research/<runId>/` へ保存する。ケース定義はtests配下へ置く。

テストで分岐を保証する固定応答と、実LLMで出力品質を比較する評価を別の結果として報告する。LocalLLMの接続が未準備なら固定経路の実装完了は認めるが、LocalLLM品質検証は未完了と表示する。

人間の比較レビューは変更前後を伏せ、回答充足、支持根拠、説明の深さ、補足の有用性、非重複、範囲遵守を各0〜4で評価する。0は欠落・誤り、1は重大な不足、2は部分的、3は実用上十分、4は具体的な強みがある状態とする。2名で評価し、同じ軸に2点以上の差があれば根拠を照合して差を記録する。レビュー担当者を確保できない場合、自己採点で代替して品質改善を宣言しない。

初期リリース基準は、重大な誤引用・明示条件違反が0件、回答充足と支持根拠が各ケースで悪化しないこと、有望な補足がある4ケース中3ケース以上で補足有用性が改善すること、補足のないケースで水増ししないこととする。既存出力が満点の場合は同点を許容するが、改善ケース数には含めない。ラウンド数と費用は併記し、増えただけで不合格にも合格にもしない。

live試験は明示的に実行する別工程とし、上記の品質基準と実usageを確認する。閾値やケースを結果を見て緩める場合は戦略versionを更新し、変更前後を残して同じ一式で再評価する。
