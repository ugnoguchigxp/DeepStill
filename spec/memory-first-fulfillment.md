# Memory中心の探索：残課題の実装と充足検証

2026-09-13。前回の内部機能実装後に残った課題を扱う。ユーザーの指定によりLocalLLM実測は対象から除外する。[前回の実装と検証](memory-first-improvement-implementation.md)の品質未達を合格へ読み替えない。

## 実探索から特定した不具合

- v2でもMemoryレビューの修復提案を無条件で再生成へつなぎ、探索方針の比較前に予算を使っていた。v2では修復を行動選択へ一本化し、v1の旧経路は保持した。
- 最初の原文範囲で主張が得られないと、残りの未読範囲を検討せず資料を終えていた。また、検索行動IDが付いた新しい取得資料では追加読解を抑止していた。どちらも、実際に読んだ範囲がある場合は次の範囲選択へ接続するよう修正した。done・取得失敗・範囲上限で停止し、未確定資料がある間は次の探索へ進まない。
- 範囲索引が各範囲の先頭80文字だけを示し、ヘッダーに続く要旨を発見しにくかった。先頭・中間・末尾の短い抜粋と資料名を索引に追加した。索引は根拠ではなく、原文取得・抽出・支持検証を必須とする。
- 行動選択が、新情報なし・既読などの候補を採用して停止していた。コードで候補を事前検査し、採用可能IDだけを選択schemaに渡す。却下理由も記録する。
- 資料選定が存在しないIDや件数不足を返した。選定・支持検証のschemaに入力ID集合と必要な判定件数を反映した。

## Episodeと評価

`query.selected` と `search.completed` をMemoryの確定イベントへ追加した。蒸留文だけに依存せず、保存イベントを `event:<id>` として検索・詳細取得できるようにした。原イベントを取得した場合は、その記録を利用側と採点側の両方に渡す。複数のIDを単一ID欄へまとめて渡さない契約も明示した。

`scripts/memory-suite.ts` は固定ケースを5件ずつ逐次実行する。各バッチの予算と全体上限を最初のmanifestへ保存し、元の研究ジョブの予算は変更しない。全件を集計し、失敗ケースの除外や成功するまでの自動再試行は行わない。生成へ評価の期待値を渡さず、開発ケースと未使用holdoutを区別する。

## 試行の記録

`data/evaluations/memory-fulfillment-live-1` は、2検索・8取得・1読解、470,513トークン・29要求で `no_information_delta` の未達終了。取得したMind2Web 2の要旨が前半にある一方、後半を読んで0主張となり、追加読解も止まった。既読かつnovel=falseの候補を採用したことも確認した。この試行は残し、上記修正の前後を区別する。

次の `memory-fulfillment-live-2` は同じ元条件（100万トークン、8検索、40取得、16読解）で実行する。終了結果・充足判定・再利用結果は、確定後に追記する。

## 予算と候補取得の追加修正

`memory-fulfillment-live-2` はWebGLMの原文から支持済み主張を回収したが、809,952トークン・43要求で未達終了した。独立監査 `memory-fulfillment-live-2-audit` は、根拠の追跡は可能だが、役割・接点・限界の説明と適用条件・リスクの裏付けが不足すると判定した。

この試行で、`research_direction_review` と `research_action_select` が予算処理上の評価として分類されず、評価中にも評価用の予約を保持していることが分かった。従来の評価役割と同様に、その評価用予約だけを解放し、最終保存用予約は維持するよう修正した。最終レビューから探索へ戻る条件にも、方針再評価に必要な予約を含めた。予算の上限は変更していない。

また、過去の検索で発見済みだが未取得の候補を `fetch_source` 行動で一件ずつ取得できるようにした。既に取得を試みたURLはコードで拒否し、保留内容の別URLからの迂回を禁止する。取得・範囲読解・支持検証・再評価は既存の逐次キューを通す。

行動選択には、直前の方針レビューで確定した候補、既知主張、問い、取得状態、未解決、予算を渡す。Memory全文と原文をもう一度重複投入することはやめ、元の検証入力は保存したまま用途を分けた。

この組合せで `memory-fulfillment-live-3` を同じ元条件で開始した。取得できた資料の違いを無視して、施策ごとの因果や一般的な品質向上を主張しない。

同試行は669,241トークン・41要求、2検索・11取得試行・0読解で `budget_exhausted` の未達終了となった。10件は `GUARD_DENIED / require_approval`、保存できたOpenReviewの1件は172文字のブラウザー確認ページで、支持済み主張は0件だった。追加の候補1件は予算予約条件により未実行となった。独立した `memory-fulfillment-live-3-audit` は必須3問をすべて未充足と判定した。

取得ガードの保留を迂回して原文を取り込んではいない。現在の `llm-fetch` 公開APIには、この保留に対する承認を完了して再取得する引数が見当たらない。取得環境の制約は、探索プロンプトを変更し続けたり、予算を増やしたりして解決済みにしない。

## 固定資料の再利用検証

検索結果に長いイベント本文を全量返すと、詳細を選ぶ前に利用側の入力上限へ達する可能性があるため、検索結果は一致箇所の短い抜粋にした。全文はオブジェクト取得で回復できる。検索用の別名もイベント種別に分け、予算や取得失敗の記録すべてを「検索語」として扱うことをやめた。長いイベント末尾の一致が検索結果に残り、詳細取得では元データを回復する回帰試験を追加した。

`memory-fulfillment-fixed` は79,693トークン・3要求で、モデルが未定義の概念IDへ関係を張り、構造検査により失敗した。元の失敗を保持し、概念段階だけを `memory-fulfillment-fixed-corrected` で再生成した。後者は概念生成とレビューで89,174トークン・2要求、構造エラー0件だった。合算費用は168,867トークン・5要求。レビュー推定点45/55/38を実測品質へ換算しない。

ワーカーの既存の1回限りの再試行に検査エラーを渡し、同じ無効出力を理由なしに生成し直す状態を修正した。存在しない参照が拒否され、その理由を受け取った再試行で有効なMemoryが保存される回帰試験を追加した。

30件の開発セットを `memory-fulfillment-development` で逐次実行する。生成済みMemoryは固定し、期待値を生成へ渡さない。新規 `llm-web-holdout-v3.json` は、凍結後の保存原文・イベントから3ケースを作成した。各軸1件にすぎないため、小規模holdoutであり一般的な性能や広いケース網羅を示さない。凍結時のハッシュは `holdout-v3-manifest.json` に保存した。

開発ケース `knowledge-06` で採点入力の不具合を検出した。利用側はEvidenceオブジェクトに含まれる原文を読んでいたが、別のevidence取得操作を省くと、採点側の `suppliedSources` へその原文が渡らなかった。このため内容は正答でも、採点側が「根拠なし」と誤判定した。Evidenceオブジェクトを取得した時点で原文位置とhashを検証し、実際に読んだ引用を利用側・採点側双方へ渡すよう修正した。未読の参照先を自動で根拠へ追加する変更ではない。修正前の試行を保持し、修正後は別manifestで評価する。holdoutはまだ実行しておらず、修正理由と凍結更新の履歴を残した。

初回開発試行は実行中のバッチを完了させ、10件・1,051,650トークンで区切った。`knowledge-10` は検索後に概要を読まず情報不足と回答し0点だった。修正後の `memory-fulfillment-development-corrected` でも `knowledge-01` が同じ手順省略で0点となったため、検索候補があるときは詳細を一件読むまでanswerを選べないschemaと実行時検査を追加した。空の検索結果からの棄却は認め、最大ステップ数は増やさない。旧結果や棄却を正答へ書き換えず、変更ごとに試行を区切る。

同試行は5件・470,545トークンで区切った。次の `memory-fulfillment-development-gated` で、検索が返す `event:<id>` を直接event取得へ渡すと空結果になる不整合を確認した。検索で発見済みの同じIDに限り、接頭辞付き・数値表記の双方を受け取るよう修正した。直接event/evidence取得後も回答可能とし、重複要求は再実行せずエラーを返して残りステップで別操作を選べるようにした。ステップ上限は維持する。

実探索3回目では、根拠0件の途中Episode生成とMemoryレビューが10呼び出し・244,328トークンを消費した。v2の根拠0件の途中評価では、生イベントを検査してdraft Memoryへ保存し、方針判定を進めるよう修正した。蒸留・レビューは最終保存時に実行する。明示的な修復行動はこの省略の対象外。原記録や最終Episodeは失わず、draftをreviewedと偽って保存しない。

`memory-fulfillment-development-gated` は実行中のバッチを完了させ、15件・1,562,343トークンで区切った。途中集計はKnowledge 90、Episode 45、Retrieval未実施、重大欠陥なし。90点超の合格ではない。新しいID処理・重複要求への応答で別試行を行う。

## 4回目の実探索

`memory-fulfillment-live-4` は同じモデル・予算で、5取得試行のうち2件を保存でき、3範囲の読解で11件の支持済み主張を得た。残る3件は取得ガードによる承認待ち。今回は最初から根拠があり、根拠0件向けの省略処理は使われなかった。取得元はBoosting Search Engines with Interactive Agentsの研究紹介とWebCPMの要旨であり、取得条件が違うため前回との差を修正の因果効果とは扱わない。

738,855トークン・40要求で `budget_exhausted` の未達終了。検索予算の消費は2だが、完了した検索は1回。次の検索を採用した後、実行時の評価用予約を確保できず停止した。行動採用時にも実行時と同じ最終用・評価用の予約を含め、Codex検索の既存予約40,000トークンを下回る見積もりで採用しないよう修正した。540,207トークン使用済みの境界で、実行できない検索を採用せず次の検索作業を作らない回帰試験を追加した。予算上限・予約額は変更していない。

独立監査の初回は質問行を重複して返し、19,342トークン消費後に検証器が拒否した。失敗を保存し、問いID・行数・主張IDを出力schemaにも反映した `memory-fulfillment-live-4-audit-grounded` で再監査した。主要概念と役割（rq1）、根拠と適用条件（rq2）は支持される一方、設計選択の判断理由・トレードオフ（rq3）が不足し、結論は `unmet`。元ジョブの未達状態を監査の部分的な支持で上書きしない。

同条件の実探索は4試行をすべて保持し、追加の無制限な成功待ち試行は行わない。修正済みの条件で固定資料の30件を `memory-fulfillment-development-final` に記録する。未使用テーマは `tests/fixtures/memory/unseen-themes-v1.json` に5種類を実行前に固定し、別ジョブとして同じモデル・各100万トークンの予算で実行する。設定予算の合計、原テーマの過去試行、テーマ定義hashを `memory-fulfillment-unseen/manifest.json` に保存した。結果を元テーマの充足へ合算しない。

## ユーザー指定による一時停止

2026-09-13、実行中の5件バッチを完了させて一時停止した。`memory-fulfillment-development-final` は30件中15件まで保存済み。Knowledge 10件の平均は100、Episode 5件の平均は55、Retrievalは未実施。Episode 04に重大欠陥があり、全体合格ではない。採点では、取得済みイベントに取得ガードの記録があるにもかかわらず、回答が証拠未提供と述べた点を指摘された。元の回答・取得履歴・判定を保持している。

次バッチの起動を止め、現在の子プロセスが完了してから親プロセスを終了した。この評価の外部呼び出しは残っておらず、自動再開も設定していない。完了ケース、各結果ファイルのhash、固定条件、残ケース、再開位置は `data/evaluations/memory-fulfillment-development-final/paused-run.json` に保存した。次は `episode-06` から残り15件。既存結果を上書きせず、同条件の残ケースを別出力先で実行して明示的に合算する。

残作業は、開発評価の残15件と未達原因の確認、未実行のholdout v3、現行評価器によるv1比較、事前登録した未使用5テーマの実探索。実探索4回目の独立監査は必須3問中2問を支持するが、設計選択の理由・トレードオフは未充足であり、探索全体の完了とは扱わない。LocalLLMの実測はユーザー指定で対象外。
