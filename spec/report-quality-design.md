# レポート生成品質を95点超へ引き上げる設計案

2026年9月12日。実装前の提案。対象は通常の実調査であり、動作検証用fixtureの文章は採点対象外とする。

## 目的と到達条件

ユーザーの問いに正面から答え、読み進めるほど理解が深まり、後から条件付きの知識と調査の経緯を取り出せるレポートを作る。本文だけで意味が通り、重要な記述は取得済み資料へ遡れることを両立する。

95点超とは、後述の固定基準で96点以上、必須条件をすべて満たし、各評価軸も配点の90%以上である状態とする。点数は品質の保証や真実の確率ではない。評価者の判断を必要とするため、機械判定による合格と、人間による確認を区別する。同じ生成モデルが高得点を付けただけでは達成としない。

今回設計するのは、調査範囲、探索の優先順位、資料の読み取り、構成、執筆、評価、改稿、候補生成と版の整合性である。モデル変更だけ、文字数増加だけ、指示文の追加だけを解決策としない。自動的なContextStill登録、新規サービス導入、検索費用の無制限な増額は含めない。既存の引用整合性検証、課金の重複防止、停止・復旧機構は維持する。

## 1. ユーザーの条件を全工程で保持する

調査開始時にResearchBriefを作り、元の依頼文、中心的な問い、対象読者、明示された必須条件、対象範囲、除外範囲、必要な下位の問い、背景説明として許す範囲を保存する。ユーザーの明示条件と、システムが補った仮定は別フィールドにする。取得した資料や関連語から明示条件を変更してはならない。

広いテーマは、定義、原理、適用例、比較、限界を調べる説明型として開始する。テーマを勝手に製品選定や導入可否の問いへ置き換えない。推定した構成は調査中に変えてよいが、範囲の変更は履歴を残し、明示条件の緩和にはユーザーの新たな指示を必要とする。

可逆圧縮の例では、中心を「元の情報を完全に復元しながら、どのように短く表現するのか。何が効き方と限界を決めるのか」とする。非可逆方式の品質設定・最適化・詳細な方式比較は対象外。違いを説明するための短い言及は許すが、それを理由に独立した探索を開始しない。

「完全復元」は対象も明記する。元ファイルの全byteか、復号後の画素値か、音声サンプルかでは条件が異なる。モード名がlosslessでも、前処理、色変換、メタデータ保持などを含めて同じ対象を比較しているか確認する。すべての専門条件を先にユーザーへ質問するのではなく、資料の記載に基づいて本文で区別する。

## 2. 関連性ではなく、問いへの必要性で探索を選ぶ

検索クエリ、検索結果、取得本文、抽出した主張、本文の各段階でResearchBriefへの適合を確認する。判定はin_scope、background_only、out_of_scope、uncertainとし、理由、対象の下位問い、参照した根拠を保存する。

- in_scope：必須条件を満たし、調査すべき問いに答える。探索候補にできる。
- background_only：対象との境界を説明するために必要。本文の短い説明に使えても、子クエリへ展開しない。
- out_of_scope：明示条件に反する、または必要な問いに寄与しない。検索・取得・採用の次の工程へ進めない。
- uncertain：モードや条件が分からない。公式資料の該当箇所だけを確認し、解消するまで本文の比較や候補生成に採用しない。

検索結果には対象外ページも混ざるため、偶然取得した資料と、対象外だと判明した後も深掘りする行為を分けて計測する。タイトルだけで可逆性を決めない。一つの資料に両方のモードがあれば、該当節と主張単位で判定する。

クエリは関連語単体で登録せず、「どの未解決の問いに答えるか」と「なぜ元の条件に合うか」を必須にする。例として「WebP」ではなく、可逆モードの仕組みや復元条件を調べる目的を持たせる。再開、追加クエリ、改稿時の追加探索にも同じ判定を適用する。

探索の優先順位は、問いの重要度、現在の根拠不足、得られる説明の増分、資料の独立性、取得可能性、費用で決める。係数は評価用事例で調整する。Claim数、ドメイン数、関連語の数を成果の代理指標にしない。

## 3. 説明に必要なまとまりで資料を読む

Claimと引用の保存は継続し、それに加えて問いごとのEvidencePacketを作る。内容は、対象、背景、仕組みまたは研究方法、具体的結果、条件、例外、他資料との関係、参照先である。定義や歴史のテーマに実験項目を強制せず、必要な項目だけ使う。

中心的な結論を支える研究は、要旨で発見した後に本文・結果表・方法へ進む。一次資料一件で確定できる仕様まで複数資料を強制しない。一方、論争や性能の優劣には、独立した根拠と比較可能な条件を求める。重要なのは資料件数ではなく、必要な問いが説明できることと、主張に見合う根拠の強さである。

同じ条件で比較できない結果は順位表へ混ぜない。取得不能なら別の原典や保存可能な公式形式を探す。それでも中心の説明に必要な根拠が不足すれば、部分レポートとして扱う。末尾に「限界」を追加するだけで高得点にしない。

説明用の仮想例は、実測や実例と明確に区別して使う。文字列の圧縮例などは計算・復元を検証する。人間の体験、研究結果、利用者の反応、調査前の仮説は記録なしに作らない。

## 4. 問いへの答えを組み立ててから執筆する

EvidencePacketを材料に、暫定的な答えと章ごとの役割を設計する。各章には「読者がこの章で何を理解できるか」「前章から何が進むか」「必要な根拠」を持たせる。同じ答えの言い換えしかない章は統合する。必須の問いが抜けた構成は執筆に進めない。

可逆圧縮なら、原理の説明、具体例、方式ごとの違い、条件付き比較、圧縮できない場合の説明へ進む構成を候補にする。FLACやWebPの紹介は、その説明に必要な場所へ配置する。調査で見つけた形式を順番に紹介する構成にはしない。

初稿は本文を連続して読める形で書く。章の数、段落の長さ、まとめの数を固定しない。一般的な「実践的含意」「反対論点」を全テーマへ強制しない。技術的な面白さは仕組みと具体例、歴史的な面白さは経緯と転換、論争の面白さは主張と根拠の衝突から生み出す。

本文の事実には主張単位の根拠を結び付ける。根拠のない事実追加は禁止するが、全段落に形式的な引用を強制してつなぎの文章まで不自然にしない。既に確認した事実をつなぐ説明・問い・構成上の案内は、役割を区別して扱う。複数の事実から導く推論には前提への参照を残す。

引用番号は読者向けには資料単位に整理し、内部では主張と引用箇所の細かな対応を保つ。「考察：」の一律表示をやめ、事実と推論の違いを自然な文で示す。主張に不可欠な条件は近くに残し、共通の制約は一箇所へ集める。注記を減らすために不確実性を隠してはならない。

## 5. 本文と調査履歴から候補を作る

Knowledge候補は単なるClaimコピーにしない。単独で意味が通る対象・主張・適用条件・重要な例外・根拠を含め、事実か推論かを明示する。一般則だけでなく、有用な個別事実も採用できる。ただし「この方法」「著者ら」だけでは対象が分からない候補は失格とする。新しい一般化は元の根拠から再検証する。

Episode候補は、初期の問い、実際に選んだ探索、得た根拠、採否判断、確認できた理解の変化、残った問いを、イベントと資料参照から作る。記録にない経験や成功談は生成しない。意味のある判断過程が残っていない場合は、抽出不能の理由を返す。Episode件数のために経緯を捏造しない。

候補にはartifactVersion、対応する本文、Claim、必要なイベントの参照を持たせる。改稿時は候補を再検証し、旧候補は旧版として保存する。旧版での採否判断を新候補へ無条件に引き継がない。本文、根拠、候補を整合した一つの版として公開する。

## 6. 固定した基準で評価し、欠陥のある工程へ戻す

以下を100点満点の提案配点とする。導入前に代表レポートと人間の評価で基準を調整し、その後は版を固定する。

| 評価軸 | 配点 | 高得点の条件 |
| --- | --- | --- |
| 依頼への適合と必要な範囲 | 20 | 明示条件を守り、必要な問いに答え、周辺情報が主題を奪わない |
| 事実と根拠 | 20 | 重要な主張全体を根拠が支持し、対象・条件・時期を取り違えない |
| 説明の深さと統合 | 20 | なぜ・どうしてに答え、具体例と比較を通じて新たな理解を作る |
| 構成と読み進める価値 | 15 | 各章が議論を前進させ、読後に中心の答えと理由を説明できる |
| 日本語と編集 | 10 | 冗長な反復、不要な専門語、過剰な注意書きが理解を妨げない |
| Knowledge抽出適性 | 10 | 主要な学びを単独で意味の通る条件付き知識として取り出せる |
| Episode抽出適性 | 5 | 実際の調査と判断の経緯を根拠付きで再現できる |

合計96点以上に加え、各軸で配点の90%以上を求める。根拠や文章の弱さを他項目の点数で埋め合わせない。読み物としての評価には、重要な問いへの回答、印象に残る具体的説明、その説明から導いた理解を評価者に記述させる。「自然な日本語だから満点」は認めない。

必須条件は点数と別に判定する。明示条件に反する内容を対象内として採用、中心的な問いへの未回答、重大な事実誤認、出典不支持、架空の経験、版の不整合が一件でもあれば不合格。背景として明示した境界説明は範囲違反とは数えない。

評価は次の三段階に分ける。

1. プログラムによる検証：参照、引用一致、版、条件判定の記録、必要な問いの対応を確認する。意味の妥当性まで機械検証済みとは表示しない。
2. 内容と編集の別レビュー：内容側は範囲・根拠・条件、編集側は構成・説明・重複・読み進める価値を判定する。本文中の具体箇所と減点理由を必須にする。評価者には過去の点数や「95点を付ける」目標を渡さない。同一モデルの別呼び出しは完全な独立評価とは扱わない。
3. 抽出と読解の確認：別の評価処理が本文から主要な問いへ回答し、Knowledgeを抽出する。本文と調査履歴からEpisodeも作り、参照資料と照合する。既存候補を見せて模倣させない。本文にない情報で補ったら失格。

評価に不一致があれば、高い方の点数を選ばず根拠付きで再判定する。中心的な内容への未解決の指摘は公開を止める。校正された人間の評価事例に対する一致度も記録する。

範囲違反は探索判定、材料不足は取得・読解、議論不足は構成、文章の重複は編集、候補不整合は候補生成へ戻す。毎回全文を作り直さず、欠陥に対応する工程を修正し、影響する主張と下流成果物を再検証する。最後に全文を通して読む。

品質改善の上限は、初期案では追加調査1巡と改稿2巡とする。効果を測って調整するが、既存の費用・時間上限を超えない。予算には最初から構成・執筆・レビュー・改稿分を確保する。上限到達時は不足を示した部分レポートまたは要改稿として返し、達成点数を捏造しない。再試行のたびに採点基準を緩めない。

## 実装順と検証

第一段階でResearchBriefと範囲判定を入れ、探索・抽出・再開・追加操作まで条件を継承する。Knowledge/Episodeの版整合性も先に直す。第二段階で問いごとの根拠と不足を保持し、件数中心の探索順位を変更する。第三段階で構成、執筆、編集、読解・抽出評価を分ける。第四段階で評価結果に応じた限定的な再調査・改稿をつなぐ。

基準用データは、可逆圧縮とLLMと宗教の既存版に加え、明示的な除外条件、否定形、複数モード、歴史の因果説明、論争、狭い仕様確認、根拠不足などを含むテーマ群を作る。開発用と未使用の評価用を分ける。採点基準を変更したら版を付け、旧版と新版を同じ基準で再採点する。特定の二テーマだけに最適化しない。

外部接続なしのテストでは、保存済み資料と固定応答を使う。可逆WebPを許し、非可逆モードと近可逆を対象内の比較から除き、モード不明を確認待ちにできることを検証する。混在資料の節単位採用、関連語で条件が消えないこと、取得不能を合格扱いしないこと、根拠のない段落を拒否すること、改稿後に旧候補が最新版へ混ざらないこと、予算上限で終了することを含める。

対象テストは `bun test tests/research-quality.test.ts tests/engine.test.ts tests/providers.test.ts` を基点に追加する。実装完了時は `bun run verify` と `bun run verify:e2e` を通す。これらの成功は構造・動作の保証であり、文章の96点達成を意味しない。

実調査の評価は資格情報を使う別工程とする。同じテーマ・入力条件・予算・評価基準で旧方式と新方式を比較し、順序と方式名を隠して読む。毎回の資料差と利用量も保存する。単一の最高点ではなく、合格率、テーマ別の最低点、範囲違反率、根拠の誤り、読解・抽出の成否、費用・時間を報告する。初期のリリース目標案は、未使用テーマ群の90%以上が96点以上、必須条件の違反ゼロ。これは実測前の目標であり、達成済みの数値ではない。

実データで「読み物として十分」と評価された見本を基準に加え、人間の判定と自動評価のずれを調べる。資料不足で達成できないテーマがあることを隠さず、合格したレポートだけに品質状態を付ける。

この文書作成時点では実装変更、レポート再生成、新方式の採点は行っていない。

## 初期実装と実測（2026年9月12日）

検索クエリ・検索結果・抽出Claimの範囲判定、初稿後の全文編集、7軸の自動レビュー、要改稿の表示、版に対応した候補生成を実装した。既存Artifactの改稿にもClaimの範囲再判定を適用する。原文の条件は各段階へ渡し、可逆・非可逆を名前だけで分類しない。判定応答のID欠落・重複は拒否する。範囲判定も意味判断はLLMに依存する。

新しいLLM呼び出しは実調査の予約・使用量・応答保存に組み込んだ。検索応答と範囲判定、抽出とClaim判定、初稿・編集・評価の間には再開可能なチェックポイントを設け、複数呼び出しで一回のWorker処理の時間制限を使い切らないようにした。不正な評価だけを再試行する場合は、正常な初稿と編集結果を保持する。
