# レポート生成処理のコードレビューと修正

2026年9月12日。対象は直近の範囲判定、初稿・編集・評価、候補生成、改稿・評価スクリプトと、それらの予算・再開・保存処理。新しい調査アルゴリズムや自動再調査の追加は対象外。

## 確認して修正した問題

| 重要度 | 問題 | 修正と確認 |
| --- | --- | --- |
| 高 | 実調査の初稿だけが保存済みでも、再開時に予算不足を無視できる | 編集・評価も保存済みの場合だけ、通信不要の再開を認める。要求回数を使い切った状態で再現テスト |
| 高 | 範囲内と判定されても検索語が空の場合、失敗応答を再利用し続ける | 検索語の必須検証を範囲応答の検証に統合。明示的な再開で不正応答だけを破棄できることを確認 |
| 高 | 中断後に成果物ID・生成入力が変わり、保存済み評価と公開する対象がずれる | 生成入力と成果物を永続化して再利用。レビュー後に中断・再開し、ID一致と評価呼び出し一回を確認 |
| 高 | 生成中に別の処理が改稿した場合、古い版番号で公開し得る | 生成開始時の成果物IDと公開直前の最新版をトランザクション内で比較。競合時は公開せず、再開時に生成状態を作り直す |
| 高 | ファイルを一つずつ公開し、失敗時に不完全な出力が残る。別の成果物が同じ版を上書きできる | Markdown・HTML・根拠JSONを一時ディレクトリに揃えてからrenameで公開。同じ版の異なるID・本文を拒否し、同一内容の再実行は保存済み出力を維持 |
| 中 | 不正な空の章・段落が構造確認を通り得る | 出力時と構造評価時にレポートスキーマ、本文参照の集合、根拠を一括検証。既存ファイルを変更する前に拒否 |
| 中 | APIへ旧版候補のIDを直接渡すと採否を変更できる | トランザクション内で最新版候補に限定して検索。旧版へのPOSTは404で、採否が変わらないことを確認 |
| 中 | 評価中に改稿されても、古い評価JSONを先に公開する | 最新版の確認を先に行い、評価ファイルを一時ファイルから置換する。完成済み本文は評価のたびに書き換えない |
| 中 | Workerの評価はDBに保存されるが、改稿は評価ファイルだけを参照する | 最新版の保存済み評価を優先し、ファイルは旧データの補助として使用。古いファイルより現在の指摘が優先されることを確認 |

公開済みの本文と根拠は版単位で保持する。変動する品質状態はDBと品質評価を正本とし、新しい静的根拠JSONには現在の品質状態を複製しない。ファイルシステムとSQLiteが一つのトランザクションになるわけではないが、完成した同一成果物の公開後にDB処理が中断しても、保存済み生成IDを用いて同じ内容を再利用できる。

## 検証

修正ごとに再現テストを追加し、再レビューを行った。最終の単体・契約テストは60件、E2Eはデスクトップ・モバイルを合わせて14件が成功。型、lint、format、ビルド、文書参照も検証対象に含めた。lintには従来のテスト内の非null断定に対する警告があるが、エラーはない。

このレビューで確認した再現可能な問題は修正済み。コード上の未発見の不具合が存在しないことや、生成文章が95点超になったことを保証するものではない。今回、外部LLMを使う追加の実調査・文章再評価は行っていない。
