# 途中レビューによる探索品質の改善

2026-09-12追記：人間向け説明案を中心にした未実装の次期案は、`memory-first-research-plan.md` のKnowledge・Episode先行設計で置き換える。本書の実行結果と実装済み変更は履歴として残す。

## 目的と合格条件

「LLMとWeb探索」の基準実行は、自動72点・目視65点だった。80点以下を失敗とし、同テーマの完成した説明として90点を目標とする。処理の正常終了、引用IDの整合、短いラウンド数だけでは内容品質を合格にしない。自動レビューの採点を目標値に誘導しない。

基準実行の記録は `data/evaluations/llm-web-live/evaluation.md`。同テーマ・同モデル・同予算で改善後を比較し、追加の試行や条件変更も記録する。

## 原因

- テーマだけの入力から作ったbriefが「関連する内容を含む」の1項目で、読者に何を説明すべきか定義できていなかった。
- 資料選定と抽出にbrief全体が渡っておらず、アクセスできた事例の詳細へ偏った。
- 検証済み情報で書ける補足を、追加検索の候補として評価した。
- 検索クエリの表記が異なると、意味の重複を判定できなかった。
- 探索中は十分と判断し、最終レビューでは中心の説明不足を指摘した。

## 改善した流れ

1. テーマを少数の具体的な読者の疑問へ分解する。テーマが広い場合は3〜5項目を目安とし、狭い質問には不要な項目を追加しない。明示された条件と推定した疑問を区別する。
2. 初回検索は元のテーマ1件で開始する。検索候補を前もって大量生成しない。
3. 資料選定にbrief、前回の充足状況、既知の主張、取得履歴を渡す。中心の説明を補う資料を優先する。
4. 選んだ資料を順番に取得・読解・根拠確認する。抽出時にもbriefと今回の問いを渡す。
5. 全件の処理確定後、現時点で書ける内容をレビューする。各問いについて、用語に触れたかではなく、根拠を使って説明できるかを判定する。
6. 追加探索候補がある場合は、独立したLLM呼び出しで既知情報との差分、元テーマへの適合、未確認の事実を再評価する。既知情報で書ける段落は執筆へ回す。レビュー結果・候補却下理由を保存する。
7. 中心の説明が不足している間は、core以外の追加探索を実行しない。有用な補足は中心の説明を満たした後に検討する。
8. 最終執筆・改稿・レビューにも同じbriefを渡す。本文だけでなく限界欄等の言語と根拠も確認する。

追加レビューは別のワーカーステップとして逐次実行する。途中の評価はキューに保存し、ユーザー候補のrevisionが変わった場合は再評価する。最終出力と途中レビュー用の予算を保留する。候補がない場合は追加レビューのLLM呼び出しを省略する。

## 検証

- 型検査・lint・format・ユニットテスト・ビルド・既存文書検査を通す。
- 「既知の補足候補を独立レビューが拒否したら次の検索を実行しない」「中心の不足がある場合は任意のトリビアを選ばない」を回帰テストする。
- 既存E2Eで進行状態の保存・再読み込みなどを確認する。
- 実探索では、各ラウンドの問い、読めた資料、充足判定、追加候補の却下理由、本文への反映を保存して比較する。

80点超でも90点未満なら目標未達。取得資料の不足を文章だけで埋めたり、自動評点を引き上げる指示で合格させたりしない。実際の生成結果に基づいて次の調整を決める。

## 実探索の結果と現在の判定（2026-09-12）

同じテーマ「LLMとWeb探索」、同じモデル `gpt-5.6-luna / low` で比較した。以下は自動評価であり、人による客観的な測定値ではない。採点の重みと合格条件を引き下げていない。

| 試行 | 自動点 | 結果 |
| --- | ---: | --- |
| 改善前 | 72 | WebGPTの事例に偏り、一般的な説明が不足。目視評価は65点 |
| 読者の問い・探索候補の独立レビュー導入後 | 58 | 中心の不足を認識したが、取得できる根拠が不足 |
| 失敗履歴・クエリ重複の制御を追加 | 64 | 5資料を読み、19主張を採用。定義・処理・比較の説明は不足 |
| 同じ根拠で改稿、レビュー指摘を引き継ぐ | 71 | 説明は改善したが、比較例が抽象的 |
| 具体的な仮例を求めて再改稿 | 67 | 具体的な問いはできたが、回答内容と根拠の対応が弱い |

すべて80点以下で、ユーザーの基準では失敗。90点を達成した実装とは扱わない。最後の67点を隠して71点だけを成果にしない。

実探索は各100万トークン上限。2回目の探索後、検索を増やさず改稿を比較するため同じジョブの上限を120万へ変更した。最終使用量は1,054,372トークン、検索6件、取得試行14件、読解5件。追加20万は編集用であり、同一予算の探索比較と区別する。

詳細は `data/evaluations/llm-web-improvement/evaluation.md` に記録する。プロンプトの各時点のスナップショットと生成レポートも保存済み。

## 次の変更案：実際の説明案を途中でレビューする（未実装）

現在の `evaluate_round` は検証済み主張から「書けるはずの説明」を評価している。実際の本文を評価していないため、充足判定と完成稿の品質が一致しない。次はプロンプトへの注意書きの追加より、この差を解消する。

### 逐次キューの流れ

選択済み資料の取得・読解・検証がすべて確定したら、`draft_checkpoint → review_checkpoint → route_gaps` を一つずつ処理する。レビューを終えるまで次の検索クエリは生成しない。全文を毎回書き直すのではなく、各必須の問いに対応する短い説明段落と引用、未解決箇所を作る。変更がない段落は再利用する。

レビューは元のテーマ、readerBrief、実際の説明案、検証済み根拠を読む。主張数・取得数・予算残量だけでは充足扱いにしない。各指摘は次の項目を持つ。

| 項目 | 用途 |
| --- | --- |
| requirementId / paragraphId | どの読者の問い・説明箇所が不足しているか |
| defect | 定義不足、工程の欠落、具体例不足、条件の一般化、引用不整合など |
| route | `rewrite` / `research` / `approval_pending` / `resolved` |
| evidenceIds | 改稿に使える既存の根拠。追加調査なら現状では足りない理由 |
| missingFact | 次に確認する具体的な事実。単なるキーワード列にしない |
| relevanceReason | その事実が元テーマの説明をどう改善するか |
| completionCriterion | 何が書ければ、この指摘を閉じられるか |

`rewrite` は検索せず既存根拠で改稿し、同じ指摘を再検査する。`research` だけが探索候補へ進み、独立レビューで重複・適合性・期待する情報差分を確認してからクエリを作る。中心の未解決項目を補う候補を優先する。中心が満たされた後は、残予算と追加価値を比較して補足を選ぶ。最短終了も予算の使い切りも目的にしない。

優先度はLLMが根拠付きで付けるが、実行可能性、重複、残予算はコードで検証する。却下理由と優先度変更をイベントとして保存する。一つの指摘が次のラウンドでも残る場合、前回の検索との差分が説明できなければ同義クエリを再投入しない。

### このテーマで閉じるべき不足

1. LLMの生成とWebによる情報取得の役割を区別し、どこで取得文書が回答へ入るかを説明する。
2. 一つの問いについて、検索語の選定、資料の採否、本文の読解、主張と根拠の対応、回答までを追えるようにする。根拠のある一般的な仕組みと、このアプリの設計提案を混同しない。
3. 同じ問いに対する単独方式とWeb併用方式の違いを示す。説明用の架空入力と条件付き出力例は明示してよいが、実際のモデル出力・測定結果として扱わない。
4. 検索漏れ、条件の誤読、弱い出典の採用、資料間の矛盾が、結論へどう影響するかを根拠とともに説明する。
5. ConfRAGは矛盾を扱う能力の評価、SAFEは生成済み回答の個別事実の評価であることを分ける。どちらもWeb併用回答の正確さ全体を保証する根拠にしない。

### SystemContextの責務を分ける

執筆側には「検証済みの事実」「その事実からの推論」「説明のために置いた仮定」を区別させる。仮例の許可を、未確認の工程や実測値を追加する許可にはしない。研究固有の結果は研究名・対象条件を残す。

レビュー側には直前の総合点や90点という目標値を渡さず、同じ基準で実際の説明を検査させる。欠陥を指摘するだけでなく、既存根拠で直せるかを必ず分類する。探索側には未解決の事実と取得履歴を渡し、編集上の不足を検索へ流さない。

### 取得制約を探索の失敗と区別する

2回目の実探索では14取得試行中9件が読解に至らず、取得ガードの `require_approval` が多かった。現在は分類を保存するが、承認待ち状態を解消する仕組みはない。利用中の `llm-fetch` の公開APIにも承認解決の入口を確認できていない。

ガードを無効化して続行しない。承認要求と通常の通信失敗を分け、URL・分類・それが必要な読者の問いを保存する。正規の承認解決APIを利用できる場合にだけ再開する。別の取得経路で同じ保留内容を読む回避策は採らない。取得可能な独立資料に探索価値があるかは通常の候補レビューで判断する。

### 予算・再開・最終判定

- 最終執筆・改稿・レビューの予算を先に保留し、途中説明案とレビューの実測消費量も次の検索の可否へ反映する。既存の固定保留量が新しい呼び出し数に足りるかを実測する。
- 説明案・指摘には根拠集合とresearch revisionを保存する。ユーザーの探索候補追加後は古い判定を採用せず再評価する。再起動時に完了済み呼び出しを重複実行しない。
- 改善探索後の最終生成は新しい成果物バージョンとして保存する。現在の「過去にsynthesizeがあれば追加しない」条件は、研究revisionごとの重複防止へ変更する必要がある。
- 90点未満なら指摘の種類に応じて改稿か調査へ戻す。ただし、予算切れ・承認待ち・同じ根拠で改善しない場合に無限再試行はしない。未達の成果物と理由を残す。
- 同テーマ・同モデル・明示した予算で再探索する。最終稿の自動点と、引用元・必須の問いへの回答を確認する目視評価を併記する。90点以上でも重大な未裏付けや未解決の中心項目があれば合格にしない。

### 実装順と必要な検証

最初に途中説明案と欠陥分類のスキーマ・永続化を追加し、次に逐次ワーカーと予算保留を接続する。その後にrevisionごとの最終生成と承認待ちの可視化を整える。最後に同テーマで実探索する。これらは次の実装範囲であり、この文書を作成した時点では未実装。

回帰テストでは、編集不足が追加検索を起動しないこと、本文が中央の問いへ答えていない場合に完了しないこと、研究revision変更で古いレビューが無効になること、再開後に新版だけを一度生成すること、承認要求を通常の再試行へ流さないこと、予算不足時に最終出力用の保留を消費しないことを検証する。
