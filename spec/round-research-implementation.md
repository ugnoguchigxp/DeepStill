# ラウンド探索 v2 実装記録

更新日: 2026-09-12。状態: 実装・固定応答による検証済み。実LocalLLMでの品質比較は未実施。

[実装計画](round-research-plan.md) / [計画レビュー](round-research-review.md)

## 実装した動作

新規Jobはv2で作成する。既存知識の確認と回答項目の整理後、テーマを起点とする1件の検索を行う。初回suggestによる派生クエリの一括生成は行わない。

LLMが検索結果から資料を選び、取得・読解・主張検証を一件ずつ処理する。8件を超える検索候補は逐次予備選別してから比較する。選出した資料の処理と主張検証が終わるまで、次の検索クエリを選出しない。

ラウンド評価では、原依頼から作った回答項目の充足と、追加探索の価値を別々に検査する。中心回答が十分でも、有用な補足・具体例・トリビアの候補と予算があれば次ラウンドへ進む。新規Claim数や少ないラウンド数を終了条件にしていない。探索目的、評価理由、本文へ採用したClaimと段落の対応を保存する。

評価入力が大きい場合は、Claim IDと条件を維持した要約を8件ずつ作る。縮約後も上限に収まらなければ、十分と偽って確定せず、確認済みの根拠による部分出力へ進む。実際のモデルの文脈容量に合わせた上限調整は必要。

## 保存と実行

- `research_work_items` に個別作業・依存・優先度・状態・revisionを保存する。Round、Brief、評価、候補、予算保留、operationごとの予約・精算は既存recordsを使う。
- `execution_slot` をDB全体で共有する。APIとCLIは登録し、provider実行はworkerへ集約する。レビュー・改稿も同じ実行枠とJob予算に含める。
- submit済みで未完了の検索は実行枠を保持する。外部結果不明時はblockedとし、lease期限だけで別処理を始めない。
- 調査を削除しても未確認の外部処理があれば実行枠はblockedのまま保持する。本文や根拠は復元せず、終了確認は `execution_events` へ記録する。確認操作は画面とAPIで提供する。
- 結果保存と後続作業の作成は制御taskのleaseを確認したトランザクションで行う。外部API自体のexactly-onceは保証しない。
- 0001.sqlは維持し、0002.sqlでキューと実行枠、0003.sqlで削除後の終了確認記録を追加した。

既存JobのengineVersion未指定は従来方式で再開する。新方式を既定から外す場合は `ROUND_ENGINE_ENABLED=0` で起動する。既存v2 Jobを旧バイナリへ渡す切戻しは行わず、新バイナリのままv2の新規作成を止める。

## 予算・失敗時の動作

ラウンド既定上限は6、検索は1ラウンド最大2件、資料選出は最大4件。残ラウンドに加えtokens、requests、documents、queries、depth等の上限を確認する。

予約の実装は、既存の「呼出し前にusageへ保守的予約を計上し、応答で精算する」方式を維持した。将来の評価・統合用の保留を別レコードとして残し、同じ金額をusageへ二重計上しない。計画書の完全なラウンド一括予約を、継続前の余力確認と操作ごとの保留付き予約に具体化した。資料の長さが判明する前に厳密な一括上限を断言せず、不足時は探索を止めて統合または部分出力へ移る。

初期の統合保留はmockで12,000 tokens、liveで総token予算の55%・最大150,000 tokens。評価保留は8,000 tokensにCodex利用時の余裕を加える。いずれも実モデルで校正する見積りであり、生成成功の保証ではない。liveでは最終工程4回分のタイムアウト余裕を探索終了時刻から分離する。

構造化応答の修正は追加1回。取得・検索GETは条件付きで上限付き再試行とし、課金POSTやLLMの結果不明を無条件に再送しない。原文一致に加え、LLMが依頼範囲と引用による支持を確認してClaimを採用する。最終レビュー不合格なら改稿・再レビューを各1回行い、未解決ならneeds_revisionの部分結果として保存する。

## API・画面

| 操作 | エンドポイント |
| --- | --- |
| 永続状態の取得 | GET /api/jobs/:id/research |
| 未開始項目の優先変更 | PATCH /api/jobs/:id/work-items/:itemId |
| 次ラウンド候補の追加 | POST /api/jobs/:id/exploration-candidates |
| 外部処理の終了確認 | POST /api/jobs/:id/confirm-external-stopped |
| 削除済み調査の外部処理終了確認 | POST /api/execution/confirm-stopped |

優先変更と候補追加はrevisionを照合し、競合は409で返す。評価中の候補追加は1回の再評価へ反映する。最終判断中の再追加と、統合開始後の追加は409にして古い評価で確定しないようにした。計画の「繰り返し追加を次境界へ持越し」よりも、受付可否を明確にする方式を採用している。

画面にはラウンド番号、中心調査／補足／トリビアの目的、現在の作業、処理済み資料数、回答十分性、評価根拠、保留予算を表示する。候補追加・優先変更・終了確認後は同じDB状態を再取得する。

## 検証

開始時の `bun run verify` は60テスト成功、E2Eは14件成功。実装後は新規ラウンドテストと既存の追加検証を含め98テスト成功。数の増加そのものを品質改善の証拠にはしない。

確認した内容は、十分になった後の有用なトリビア探索、12種類の固定判断ケース、選出全件処理、範囲外Claimの拒否、優先変更の競合、評価途中の追加、予算不足時の部分出力、上限付き応答修正、最終レビューと改稿、停止再開、複数プロセスの排他、既存Job互換、migration再適用、調査削除との競合。liveモードのパイプラインも固定providerで試験したが、外部の実モデルを呼んだ試験ではない。

`bun run verify:e2e` ではデスクトップ・モバイルのラウンド評価表示とリロードを含む17件が成功。モバイル向けの既存削除テスト1件はテスト定義によりskip。画面スクリーンショットも確認した。

新旧進捗のfixture混在でE2Eが2件失敗した際は、従来方式の進捗テストをengineVersion=1に固定し、新方式の表示・リロードテストを別に追加して再検証した。調査削除と外部処理の排他が競合した際は、削除を維持しつつ未確認の外部実行だけをblockedとして保持するよう修正した。

検証ログは `data/evaluations/round-v2-implementation/` に保存する。既存テストの非nullアサーションに対するlint警告とPDF fixtureのフォント警告は残るが、検証コマンドは成功している。

## 残る実測

LocalLLMの設定は既存のchat-completions互換Adapterを利用する。モデルの配備・選定は今回の対象外であり、実機の停止確認能力、文脈容量、速度、予算見積り、補足の実際の有用性は未測定。2名の人間による盲検品質比較も未実施であり、固定テスト成功で代替したとは扱わない。

CodexSearchは外側の呼出しを逐次化しているが、その内部探索の並行性・回数は制御できない互換経路として扱う。厳密な単発検索はDataForSEO等の明示的なsubmit/poll経路を用いる。同じLocalLLMサーバーを別アプリや別DBが利用する場合は、この設置の排他制御の対象外。
