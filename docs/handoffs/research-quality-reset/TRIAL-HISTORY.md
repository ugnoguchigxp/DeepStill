# 探索品質改善トライアル履歴

最終更新: 2026-09-17

この文書は、探索品質を改善するために何を試し、何が実際に変わり、なぜ採用または不採用になったかを辿るための索引である。点数だけで候補を並べず、正常完了、内容の正確さ、費用、変更分岐への到達、外部条件を含めて判断する。

詳細な採点や生ログを置き換える文書ではない。事実確認はリンク先の実験記録と `data/evaluations/` の `run-detail.json` を優先する。

## 状態の意味

|状態|意味|
|---|---|
|採用済み基準|品質改善の出発点としてmainへ取り込まれた状態。品質目標達成を意味しない|
|暫定保持|コードはmainに残っているが、比較不足などにより最終採用を宣言していない|
|不採用|候補コードを保存したうえでmainからrevertした|
|採用保留・比較不能|外部条件差や候補分岐未到達のため勝敗を判定できず、mainには残していない|

「候補実行の点が高い」ことと「変更が点を上げた」ことは別である。変更した分岐へ到達していない試行、検索結果や取得成否が大きく異なる試行、候補だけ資料が増えた試行から因果効果を主張しない。

## 現在のコードに残ったもの

### 採用済み基準

2026-09-13の復元版を、その後の比較の基準として採用した。復元試行は70点だったが、取得済みURLの再選択と訂正失敗により `partial / invalid_deliverable` で終わった。したがって「70点版」は合格版ではなく、比較の出発点である。

それ以前に、次の基盤変更は通常実装として残っている。

- deliverables-v1で、読んだ本文からレポートとKnowledgeを更新しながら次行動を選ぶ。
- 長文の連続読解、読了済みreadの候補除外、HTML本文リンクの候補化。
- 新規本文があるときはdraft更新を必須にし、navigationだけなら `draft:null` を許す。
- 行動エラーと成果物エラーを区別し、入力・出力別の予算と実測精算を保存する。
- llm-fetch 0.1.1と、未読・保留を回避せず記録する取得ガード。

これらは現在の仕組みを説明するものであり、個々の品質寄与を今回の固定基準で再証明したものではない。

### 暫定保持中のS4C

S4Cは唯一、比較実験後もmainへ残っている候補である。理由は、引用元IDの有限候補化が機械的な不変条件として妥当で、固定診断でも狙った誤りを防いだからである。

一方、live比較では基準側にも引用IDエラーが発生せず、DeepSeekの+2点と画像の+11点をS4Cの効果とは断定できなかった。候補は費用増や正常完了の悪化も伴い、4テーマ各2対の採用検証も未完了である。したがってS4Cを「品質改善として採用済み」「80点達成」と表現してはいけない。

### 固定再生基盤R6と採用保留U3

R6は保存済みoperationの入力を再利用し、成果物更新だけを同じ資料で比較できる評価基盤として採用した。live探索を置き換えるものではなく、探索・取得・終了判断の改善判定には使わない。

U3は、全文再生成で起きていた無関係な節の脱落をコード境界で減らす候補である。固定再生では明確に改善したが、liveではモデルが全節を明示置換し、保持改善は確認できなかった。したがって採用保留とし、mainでは `DELIVERY_SECTION_UPDATES=1` を指定した場合だけ有効にする。探索品質全体の改善とは扱わない。

## 失敗から分かったこと

### 1. プロンプトで指示しても、状態上不可能な行動は起こせない

初回検索timeout後の実行では、SystemContextが別検索を勧めても `searchUnavailable` と残query 0が渡され、モデルは検索できなかった。検索回復は文章の強化ではなく、エラー分類、残予算、再試行回数、利用可能操作の状態遷移として直す必要がある。

L1は状態遷移を変えて別検索を実現したが、外部のbot challengeが続き内容は増えなかった。回復分岐が動いたことと、最終成果物が改善したことを分けて記録する。

### 2. 局所的な機械改善だけでは採用できない

A1は拒否URLからの訂正、P0はDB状態の整合、S4Cは不正sourceId拒否、SystemContext S1はKnowledgeの `rule / skill=null` 化に成功した。しかし、いずれもその局所効果だけでは正常完了率、内容点、費用を同時に改善できなかった。

テストや固定入力再生は不変条件の確認には使える。新規live探索の品質改善を代替するものではない。

### 3. 「もっと具体的に」「既存内容を保持」は副作用が大きい

S2では具体例が増えた一方、比較対象の取り違えと誤訳が発生し、探索と生成が長期化した。S3では最初の統合時に既存段落を保持できたが、その後の全文再生成で引用IDが壊れ、新資料を含む稿を保存できなかった。

要求を追加するだけでは、正確さ、保存、終了、費用を保証できない。全文を毎回再生成する契約では、一つの追記指示が既存節、引用、Knowledge、次行動のすべてへ影響する。

### 4. SystemContextの短縮はtoken削減と同義ではない

最新S1では執筆用Contextを56.2%短縮したが、navigation呼び出しが5回から14回へ増え、比較可能な試行の入力tokenは67.5%増えた。1回当たりの固定文を短くしても、行動回数、草稿サイズ、取得失敗、訂正回数が増えれば総費用は悪化する。

次回は「執筆規則の圧縮」と「次行動・終了規則の変更」を同じ候補へ混ぜない。SystemContext文字数、呼び出し回数、呼び出し用途別tokenを別々に測る。

### 5. invalid_deliverableは一種類の問題ではない

過去に確認した主な停止原因は次のとおり。

- `URL_ALREADY_ATTEMPTED`: 取得済み・拒否済みURLの再選択。
- `INVALID_SOURCE_REFERENCE`: 存在しない、または1文字欠けたsourceIdの引用。
- `SKILL_REQUIRES_PROCEDURE`: rule相当のKnowledgeへ不完全なSkillを付与。
- `WITHHELD_SOURCE_ALIAS_USE_INDEPENDENT_EVIDENCE`: 保留資料の別名・由来を独立証拠として扱えない状態での訂正失敗。
- schema不一致や不正なread/fetch/search選択。

エラー名だけを訂正入力へ返す方法は、同じ失敗の反復を止められないことがある。失敗した操作、未実行であること、選択可能な候補、禁止理由、回復後に保持すべき有効稿を構造化して渡す必要がある。ただしA1/S1のように修正用呼び出しを増やす場合、全体費用と内容退行も測る。

### 6. 有効な途中稿があっても、最終状態は失敗し得る

複数試行で、根拠付き本文とKnowledgeが保存された後、次行動または最終訂正が失敗して `partial / invalid_deliverable` になった。内容点だけを見ると改善に見えるが、利用者は正常完了と誤認しやすく、後続処理も不安定になる。

評価では、最後の有効成果物の内容点と、jobの終了状態を別に記録する。内容点の上昇で正常完了率の悪化を相殺しない。

### 7. 全文更新は「追加」と同時に「消失」を起こす

過去には、具体例や新しい公式情報を追加した版で、以前の条件、料金、機構説明、比較、注意事項が脱落した。単純な文字数維持も解決にならない。冗長記述は消してよい一方、根拠付きの別論点を新資料と無関係に落としてはいけない。

次回は節単位の安定IDや、変更対象外の節をコード側で保持する方式を検討する。本文全体の「必ず保持」という指示だけを再追加しない。

### 8. Episodeも検証対象である

Episodeが、URL行動の失敗を「ユーザー指定の成果物形式が不正」と取り違えたり、ガードで全文未読の資料を部分読解扱いした例がある。Episodeはレポートの要約ではなく、実際の判断、失敗、回復、結果、未解決を記録するものなので、eventとの一致を確認する。

### 9. 外部条件差を候補の効果にしない

DuckDuckGo timeout、bot challenge、取得ガード、404、外部LLM timeoutにより、同じテーマでも読める資料が大きく変わった。候補だけ検索成功して90点になった試行や、候補だけ資料0件になった試行がある。変更分岐へ未到達の対は採否から除外する。

同日実行だけでは十分でない。共通URL、本文hash、失敗操作、候補分岐への到達を照合する。採用候補は基準→候補と候補→基準の順序を入れ替え、複数テーマ・複数対で確認する。

### 10. 部分更新schemaだけでは、部分更新は保証されない

U3のlive試行では、節単位の操作を要求しても、モデルは新資料が関係すると判断した全3節を置換した。schemaが全文draftを禁止しても、全節のreplaceを許せば実質的な全文再生成になり得る。

一方、置換数を機械的に1件へ制限すると、複数節に及ぶ訂正や反証を取り込めない。保持率だけを目標にせず、固定再生のような「新資料と無関係な節」が分かる条件と、liveで本当に複数節へ影響した条件を分けて評価する。

### 11. 初回queryの改善だけでは、探索全体の改善にならない

Q1では、短い製品名 `duck db` を `DuckDB definition` に直すことで高密度な公式ページへ進めた。一方、既に明確な `可逆圧縮` は同じ資料のまま計画費用だけ増え、広いテーマ `local llm` は公式資料を増やした後も取得失敗と未解決点を追い続け、要求数とtokenを大幅に増やして最終失敗した。

queryの見た目の良さ、一次資料数、Knowledge件数を個別に採用根拠にしない。最初のquery、検索結果集合、URL選択、読後の情報増分、停止判断、最終成果物を一続きで評価する。ただし次の実験では一要因ずつ変え、query生成とURL選択・終了制御を同時に変更しない。

## 次の改善で優先すること

1. `WITHHELD_SOURCE_ALIAS_USE_INDEPENDENT_EVIDENCE` と `URL_ALREADY_ATTEMPTED` を、自由文の注意ではなく回復可能な状態遷移として設計する。
2. navigationの候補を実行可能なsourceId・URLへ制約する。ただし候補欠落、schema肥大、探索多様性の低下を独立に測る。
3. 節単位の安定IDと部分更新を導入し、新資料と無関係な既存節をコードで保持する。S3の保持指示をそのまま復活させない。
4. 執筆SystemContextのKnowledge規則だけを小さく試し、探索継続・終了規則は変更しない。最新S1の全プロンプトをまとめて再適用しない。
5. 外部検索障害の回復は、最大1回など明示した回数、異なるquery、費用上限、連続失敗時の停止を持つ。L1をそのまま採用せず、bot challengeを含む実際のエラー分類を見直す。
6. Q1全体を復活させず、検索結果内のURL選択だけを対象に、期待情報密度・一次性・既読資料との非重複を比較する小さな候補を先に試す。

## 次回トライアルの最低記録

- 基準コミット、候補コミット、保存ブランチ、revertまたは採用コミット。
- 仮説が対象にするevent・operation・エラーと、候補分岐へ実際に到達したか。
- 同一テーマの基準と候補について、URL、本文hash、取得失敗、最終成果物版を比較した結果。
- 内容点と内訳、正常完了、重大な引用誤り、途中稿からの消失、Knowledge、Episode。
- 入力・出力token、要求数、query、URL、保存資料、実行時間。予約を実測へ加えない。
- SystemContext、作業データ、schemaのサイズと、用途別のLLM呼び出し回数。
- 「局所的には改善したが不採用」の場合、再利用できる部分と、そのまま復活させてはいけない部分。
