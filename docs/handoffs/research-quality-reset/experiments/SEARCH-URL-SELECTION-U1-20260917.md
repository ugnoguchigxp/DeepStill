# URL選択U1トライアル（2026-09-17）

## 仮説

現行deliverables-v1は検索候補のtitle・snippet・URLを渡し、LLMにfetch URLを文字列で返させている。SystemContextには候補比較の指示があるが、どの候補が高密度か、一次資料か、既読資料と重複しそうかを選択結果として残さない。そのため、順位や目立つ語に引かれた選択、短い索引、同じ出所の反復、URL転記・未発見URLの失敗が起きても、選択判断を検証しにくい。

U1ではquery生成、検索、取得、読解、成果物更新、予算、終了条件を変えない。fetch時だけ、実行可能な検索結果・本文リンクへ安定candidate IDを付け、LLMにはURLではなくIDを選ばせる。同じ応答で次を明示させる。

- その資料から増えると見込む情報の種類。
- 公式・一次、独立した二次資料、索引・ナビゲーション、または不明のどれか。
- 既読資料に対して新規、続き、重複見込み、または不明のどれか。

これらは検索snippetから得た選択用metadataであり、レポートの事実根拠には使わない。追加のLLM呼び出しは行わない。

## 期待と不採用条件

期待する結果は、queryと検索結果集合が同じ条件で、中心質問を複数埋められる高密度資料、公式・一次資料、既読資料と異なる増分を持つURLが先に選ばれ、取得失敗・低密度資料・重複資料が減ることである。

次のいずれかなら不採用とする。

- 3テーマのいずれかで、最終レポート、Knowledge、Episode、正常終了が基準より悪化する。
- 選択理由の出力だけ増え、実際のURL、読後の情報増分、成果物が改善しない。
- 候補ID制約で有用なURLや探索多様性を失う。
- query、検索回数、終了条件など、URL選択以外の要因が変わる。
- 入力・出力・要求の増加に見合う成果物改善がない。

## テーマ別の影響

### local llm: 最終成果物は改善したが、選択予測は不正確

基準と候補の初回検索結果8件は同一だった。候補はAI-Pediasとnote.comの2資料を保存し、基準はnote.comとOllama公式context-lengthの2資料を保存した。

- 基準の `partial / unresolved_questions` に対し、候補は `completed / satisfied`。
- query 4→2、URL 9→7、要求31→21、入力134,974→99,667（-26.2%）。出力は8,752→9,946（+13.6%）。
- レポートは13→20段落、1,483→2,890文字、Knowledge 2→3。候補は概要、メモリ見積もり、量子化、ツール導入、モデル例、トラブル対処を一つの説明へまとめた。
- 一方、候補は類似した解説記事を連続して選び、7回のfetch予測をすべて `new_question` と記録した。取得失敗後もKoromo、Qiita、AI-Pedias、ITlibra、Techmania、note.comを重複見込みなしと評価しており、U1のnovelty判定は実際の候補類似性を識別していない。
- 最終改善は認めるが、「重複の少ない候補を選べた」という仮説までは支持しない。基準側の4回目検索はbot challengeになっており、検索継続条件の外部差もある。

### duck db: 費用を少し減らしたが、公式資料の範囲と成果物が後退

初回検索結果は8件すべて共通で、順位だけ一部異なった。したがって候補が高密度URLを選べたかを直接比較できる。

- 基準は公式トップから公式Documentation、Install、Client Overview、Python Install、SQL Introductionへ進み、公式6資料を保存した。候補は公式トップ、Installの後、20,238文字のZenn入門と7,894文字のQiita記事を選び、4資料を保存した。
- 候補は独立解説1件からOLAP/OLTP、JSON、永続化、同時接続の制約をまとめた点では情報密度が高かった。
- 一方、基準にあったSQLのWHERE/GROUP BY/HAVING/JOIN/UPDATE/DELETE、クライアントのサポート階層、クライアント間のSQL・ディスク形式互換性、Python導入・DataFrame例が候補から脱落した。候補も列指向を挙げるだけで、分析が速い仕組みを説明していない。
- URL 7→4、資料6→4、要求19→14、入力161,372→158,809（-1.6%）、出力18,507→16,485（-10.9%）。しかしレポートは15→10段落、1,812→1,155文字（-36.3%）、Knowledge 4→3となった。終了は両方 `partial / unresolved_questions`。
- 26.3%の要求削減に対して、広い原依頼へ答える公式根拠と説明範囲の減少が大きい。高密度な二次資料を選ぶことが、複数の一次資料で別々の必要事項を埋める代わりにはならなかった。

### 可逆圧縮: 最終状態は候補が良いが、同条件の勝敗は比較不能

初回検索結果は7件が共通だった。候補はWikipedia取得失敗後、Aetheriaの8,103文字の記事1件を読み、定義、RLE/LZ、形式例、用途、非可逆との使い分けを659文字にまとめて正常完了した。

検索成功後の基準 `c2143415-5b59-4912-8add-6e2893e6c72c` は、E-Words、別解説、Deflate図解の3資料を保存し、LZ77・ハフマン・Deflateの追加検索まで進んだ。最後の図解を統合するLLM operationが約5分後にabortされ、jobはfailedになった。最後の有効途中稿は1,268文字で、圧縮済み形式の再圧縮、圧縮率・速度・メモリの条件、用語上の注意まで候補より広かったが、最終Episodeは作成されていない。

候補の正常完了は事実だが、基準の外部LLM abortをU1の勝ちにはできない。また候補は高密度な1記事で早く満足し、基準が見つけたアルゴリズム機構の深掘りへ進まなかった。今回の対は正常終了比較から除外する。

## 選択metadataの実測

候補3試行のfetchは合計13回だった。novelty予測は `new_question` が12回、`continuation` が1回で、`likely_redundant` と `unknown` は0回だった。local llmの類似記事群、DuckDBの同一公式サイト内のトップとInstall、可逆圧縮の一般解説2件でもほぼすべてを新規質問扱いした。

候補IDの有限集合化は動作し、候補外URL、URL転記、`UNDISCOVERED_URL`、`URL_ALREADY_ATTEMPTED` による失敗は発生しなかった。ただし基準側にも今回これらのエラーはなく、最終品質の改善根拠にはならない。自己申告のsourceRole・noveltyを追加するだけでは、候補間の相対比較や重複抑制を保証できなかった。

## 判断

**U1は不採用。候補コードを保存したうえでmainからrevertする。**

`local llm` では明確な最終改善があった。しかし `duck db` では、ほぼ同じ入力費用のまま公式資料による説明範囲、段落、本文、Knowledgeが後退した。「1テーマでも成果物が悪化した場合は不採用」という条件に該当する。可逆圧縮は外部abortで比較不能だが、不採用判断を覆さない。

再利用できるのは、fetchを実行可能な候補IDへ制約し、選択理由をeventへ保存する機械的部分である。ただし、これだけを品質改善として再採用してはいけない。再検討時は、各候補を独立に `new_question` と自己申告させるのではなく、同じ候補集合を相対比較し、各未解決点をどの候補が埋めるか、既読資料と何が重なるかを一覧で判定する必要がある。その判定自体の追加費用と、一次資料を複数読む価値を失わないことも評価する。
