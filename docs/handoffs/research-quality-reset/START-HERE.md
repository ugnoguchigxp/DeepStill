## 2. 継承すべきユーザー要件

- 最重要は、実際の探索によって問いを満たし、読者にとって十分な内容を持つ結果を得ること。テスト通過や形式の完成だけでは完了しない。
- 検索エンジンと検索結果だけを中心にしない。読んだHTMLに続き、原典、具体例、仕様等の有用なリンクがあれば優先する。ただしリンクを辿ること自体を目的にしない。
- 未解決の重要な問いと予算が残るなら、別の切り口や独立資料を検討する。予算を使い切ることは目標ではない。
- 価値のある出力はレポートとKnowledge・Episode。中間の採点表・概念カード・方向審査等を量産するために研究プロセス内のLLMトークンを使わない。探索に必要な行動判断や本文読解は必要な処理として区別する。
- Knowledgeは再利用可能なまとまりにする。小さな事実の断片や、論文の結果を一般的な推奨に変えたカードは不十分。
- procedureを出すなら、適用場面、入力・前提、工程、判断分岐、確認方法を備えたSkillとして使える形にする。根拠が足りなければ無理に生成しない。
- Episodeは今回の調査全体で1件。検索1回や資料1件ごとに増やさない。レポートをEpisodeへ名前だけ変えて転記しない。
- レポートは問いに答える読み物であり、調査履歴の羅列ではない。何が分かったかを、仕組み、具体例、条件、比較、限界とともに説明する。レポートとEpisodeの役割の違いが読者に分かること。
- 毎回、探索経路を時系列に分解し、LLMの選択が合理的だったかを分析する。最終出力と件数だけで採点しない。
- 研究の入力上限1,000,000、出力上限100,000トークン。キャッシュ入力・推論出力を二重加算しない。予約と実測を区別する。
- LocalLLMの実測は対象外。通常API・worker・WebUIへ記録される新規Web探索で検証する。
- llm-fetchが原因なら、再現可能な正式な改修依頼書まで用意できる。ただし、未読・保留だけで誤検知とは決めつけない。
- 明示依頼なく、他の既存Codexタスクへメッセージやプロンプトを送らない。

旧仕様の「90点」「複数のEpisode」「中間評価・Concept等をLLMで作る」は、後のユーザー要件と同一ではない。現在の目標は80点超え。旧仕様をそのまま復活させない。

## 5. 白紙からの分析手順

### A. 先に評価基準を固定する

原依頼から「読者が何を理解できれば価値があるか」を短く定義する。KV Memは曖昧なので、意味を断定する根拠、候補を区別する説明、どこまでを答えとするかを明示する。自分の想定した意味をユーザーの明示要件へすり替えない。

成果物を詳しく読む前に配点と評価観点を書き、日時付きで保存する。既存の配点の利用は必須ではない。変更する場合、過去の点数との単純比較はせず、旧結果も新基準で採点し直す。80点を超えるように基準を後から緩めない。

探索の合理性、根拠の支持、説明の深さと読みやすさ、Knowledge・Episodeの再利用性、費用に見合う情報増分を扱う。重大な捏造や中心の問いの未回答を、文章の流暢さで相殺しない。

### B. 行動台帳を時系列に再構成する

eventsの時刻とIDを基準に、operation開始・完了・失敗を結び付ける。delivery:10をdelivery:2より前に置くような文字列順ソートをしない。

一行は検索、取得、読解、生成、修正、終了などの実行単位とする。次の項目を記録する。

| 項目 | 確認する内容 |
| --- | --- |
| 時刻・ID | event、operation、成果物版との対応 |
| 判断前に見えていたもの | 問い、候補URLと発見元、本文リンク、読了範囲、失敗、残予算 |
| LLMの選択と明示理由 | 応答に保存されたaction、purpose等 |
| 実行制約 | スキーマ、読了制御、ガード、予算、深さ、失敗上限、プログラムの強制分岐 |
| 実行結果 | 成功、未読、失敗、結果不明を区別 |
| 情報増分 | 新しい説明・条件・反証等か、同一記述の重複か |
| 現実に選べた代替 | 当時発見済みだったリンクや可能な検索。後知恵のURLを使わない |
| 費用 | 入力・出力実測、予約、不明分、処理段階 |
| 判断評価 | 合理的／不合理／情報不足と、その根拠ID |

LLMの内部思考は取得できない。purposeは説明された理由であって、本当の内部原因と断定できない。プログラムがfinishを強制した場合と、LLMが十分と判断した場合を分ける。

### C. 探索の広さと深さを別々に評価する

URL数、ドメイン数、保存件数をそのまま情報源の独立性にしない。同じ論文の要旨・PDF、同じREADME、同一プロジェクトの文書・論文、forkやmirrorを識別する。

続きの読解は同一資料でも新情報があれば有益。逆に別URLでも重複なら増分は小さい。分岐数を増やすだけの無関係な探索にも加点しない。

取得済み、抽出済み、LLMに渡した範囲、引用された範囲、意味を検証した範囲を分ける。UTF-16カーソル、UTF-8バイト数、トークン数を混ぜない。PDFのpartial抽出と未読ページも別物として確認する。

### D. 成果物がどう変わったかを追う

最終レポートだけでなく本文読解直後・修正後・終了時を比較する。増減した主張、根拠、具体例、適用条件、限界、Knowledgeを特定する。

文字数は検出の手がかりであり品質指標そのものではない。短くなった場合は冗長な記述の整理か、必要な説明の消失かを原文と照合する。長くなった場合も重複・留保・数値の羅列を点検する。

引用は位置一致に加え、対象、母集団、条件、指標、時点、推論の範囲が主張を支えるかを確認する。検索スニペットや未読ページが事実の根拠に紛れていないかを見る。

Knowledgeは新しい利用者がその単位だけを取り出して正しく使えるかを評価する。Episodeは調査全体1件で、実際の失敗・判断・結果・未解決を回復できるかを確認する。件数だけでは合格させない。

### E. SystemContextを実入力と合わせて評価する

指示全文だけでなく、役割、生成スキーマ、渡された状態、使用可能な操作、プログラム側検証との組み合わせで評価する。

- 指示が競合していないか。固定例や語彙が探索対象を不当に狭めていないか。
- 行動判断だけの呼び出しへ全文草稿や大きな執筆契約を渡していないか。
- 「未読」「失敗」「未解決」「終了」を正しく伝えられているか。
- LLMに任せる意味判断と、コードで保証すべき不変条件の境界は適切か。
- 現在の入力だけで指示を実行できるか。必要な状態が欠けているのにプロンプトの強化で補おうとしていないか。
- プロンプトへ注意を追記するたびに入力費用と矛盾が増えていないか。

問題を、取得サービス、探索制御、状態表現、プロンプト・スキーマ、成果物更新、会計、UIに切り分ける。一つの外部要因で全欠陥を説明しない。

### F. 最初の評価を保存し、その後に履歴を読む

独立評価には「観測事実」「解釈」「原因仮説」「未検証」を明記する。原因を断言するなら、同じ条件でどの反証を調べたかを書く。

ここで初めてHISTORY.mdを読む。一致した結論、異なった結論、過去の分析が見落としていた点を追記する。独立評価の初版を上書きして過去の結論に合わせない。

## 6. 改善・再検証の進め方

1. 一つの観測された欠陥について、入力から誤結果までの因果をコードとログで結ぶ。
2. 「これを変えると次のどの行動・成果物が変わるか」という反証可能な仮説を書く。コード、状態表現、プロンプト、外部依存のどこを直すかを比較する。
3. 関係する最小の回帰試験を作り、機械的に保証できる不変条件はコードで保証する。単なる出力文言や実装の写しをテストにしない。
4. 大きな設計変更が必要なら行ってよい。ただし何をまとめて変えたかを記録し、単一要因の効果と断言しない。テーマ固有のURLや答えを埋め込んで合格させない。
5. 関連試験とbun run verifyを通す。ソース・lockfile・実行設定のハッシュ、差分、モデル、SystemContextの版を保存する。
6. 通常API・workerから新規Web探索を行い、WebUIで履歴・レポート・Knowledge・Episode・使用量を確認する。
7. 同じ行動台帳と成果物差分を作って再評価する。総合点だけでなく、予測した改善が起きたか、退行はないかを判定する。
8. 改善が確認できなければ原因仮説を更新する。停止上限の引き上げや注意文の追加を無条件に繰り返さない。
9. 80点超えでも一回の偶然で完了にしない。確認再実行、または別テーマの転用試験で主要な改善が保たれるかを調べ、未検証の範囲を明記する。これは今回提案する再現性確認であり、過去に満たされた条件ではない。

fixtureは制御分岐の検証、保存資料再生は執筆・メモリ生成の検証、新規Web E2Eは実探索の検証として扱う。同一条件とは呼ばない。モデル変更、予算変更、取得内容の変化、別作業のコード変更があれば比較条件に記載する。

研究内に新しい採点LLMやレビュー会議を追加することと、開発セッションでログを分析することは別である。前者はユーザーの費用・出力要件を満たす設計か慎重に見直す。

## 7. 通常E2Eの再現方法

サーバーが停止しておりアクティブな外部呼び出しもない場合は、リポジトリルートでbun run devを使える。標準検証で.envの更新時刻等が変わりworker.staleになることがあるため、検証後に必要に応じて再起動する。実行中に再起動しない。

最新実行と同じ予算条件で新規作成する例：

```sh
curl -sS -X POST http://127.0.0.1:4310/api/jobs \
  -H 'Content-Type: application/json' \
  --data '{"topic":"KV Mem","mode":"live","budget":{"queries":8,"rounds":8,"documents":16,"urls":24,"inputTokens":1000000,"outputTokens":100000,"requests":80,"wallMs":1200000,"depth":4}}'
```

返された実際のIDを使用する。GET /api/jobs/<ID>で詳細、http://127.0.0.1:5173/?job=<ID>でWebUIを確認する。他の上限を変える場合は比較条件へ記録する。LLMはWeb探索を実行するので、研究側の実呼び出し使用量を必ず集計する。

試行ごとに別ディレクトリへrun-detail.json、設定と差分の記録、行動台帳、成果物差分、評価、改善仮説と検証結果を保存する。過去のrun-detail.jsonを新しい実行で上書きしない。不明な使用量を0に置き換えない。

## 9. 新しいセッションに求める成果物

- 独立評価の初版と、評価方法を選んだ理由。
- 過去の分析との比較。過去の採点を踏襲しなかった場合も理由を残す。
- 実行ごとの時系列台帳と、LLMが明示した判断理由の評価。
- 実装変更・SystemContext変更・回帰試験・通常E2Eの記録。
- WebUIに残る実成果物へのリンクと、根拠付きの最終評価。
- 未解決の原因、外部依存の再現可能な依頼書、各試行と全体の使用量。

達成できていない場合は、そのまま未達と報告する。試験合格、長文化、URL件数増加、ガード解除、予算消費量の増加を、ユーザーの求める品質向上の代わりにしない。
