# DeepStill：AIによる改善提案・実装・比較評価の共通ガイド

更新日：2026-09-14。リポジトリ：`/Users/y.noguchi/Code/deepStill`。

実施済み候補の採否と再発防止事項は [TRIAL-HISTORY.md](TRIAL-HISTORY.md) を参照する。候補を実装する前に、同種の変更が既に不採用または採用保留になっていないか確認する。

## 目的と仕組み

DeepStillは、テーマからWeb検索・資料取得・読解を繰り返し、レポート、再利用可能なKnowledge、調査全体のEpisodeを生成するアプリケーションである。通常の探索は `deliverables-v1` 経路で動く。

目標は、比較的推論能力の低いLLMでも繰り返し使える探索の仕組みを作り、固定評価で80点以上の品質を複数テーマで確認すること。現在は探索モデルを **gpt-5.6-luna / reasoning low** に固定する。提案・実装を担当するAIは変更してよいが、探索モデルの変更と混同しない。LocalLLMでの実測は今回の必須範囲ではない。

特に検討したいのは、エージェント周辺の実装とSystemContextである。常設指示を小さくし、必要な局面に必要な状態・指示・操作だけを渡す設計、状態保存、具体的な失敗フィードバック、回復処理、成果物更新を検討する。ただし、短い指示やhooks自体が品質を上げるとは前提にしない。実際の入力と行動で効果を確かめる。

## 他のAIへ渡す依頼文

> この文書を読み、DeepStillの探索品質を改善する案を出してください。まず現在のコードと生ログから欠陥を調べ、自分の仮説を保存してください。その後に過去の仮説・評価と照合してください。案ごとに、観測した問題、変更内容、期待する行動の変化、反証条件、費用・品質のリスク、検証方法を示してください。提案だけの依頼ならそこで止め、実装まで依頼された場合は本書の保存・比較・差し戻し手順に従ってください。探索モデルはluna/low、作業はmainです。採点を上げるために基準を緩めたり、テーマ固有の答えを埋め込んだりしないでください。

複数AIの提案は独立に保存し、出所を記録する。複数AIが同時にmainや同じDBを変更・実行しない。提案を集める段階と、選んだ案を順番に実験する段階を分ける。既存の別Codexタスクへの送信、新しいタスクの作成、定期自動実行は明示依頼がない限り行わない。

## 守る要件

- レポートは問いに答え、仕組み・具体例・条件・比較・限界を説明する。調査履歴や数値の羅列で代用しない。
- 検索結果だけで終わらず、読んだ資料から原典・続き・仕様・具体例へ進む。URL数や分岐数自体を目標にしない。
- Knowledgeは単独でも正しく再利用できるまとまりにする。手順を生成するなら前提・工程・分岐・確認方法を備え、根拠不足なら無理に作らない。
- Episodeは調査全体で1件。実際の判断・失敗・回復・結果・未解決を残し、レポートの転記にしない。
- 研究ループに採点LLM・審査会議・中間カードの量産を追加しない。開発側での評価とは区別する。
- 未読資料・検索スニペットを読了した一次資料として引用しない。ガード解除、捏造、終了状態の偽装で点数を上げない。
- テーマ固有のURL・答え・成功例を実装やプロンプトへ埋め込まない。
- 既存の無関係な差分を消さない。外部LLM要求が動いている間はサーバーを再起動せず、予約やexecution slotを根拠なく消さない。

## 実験の手順

1. 初回だけ `initial_instructions` MCPを実行する。利用できなければ記録し、ローカルAGENTS.mdを確認する。git状態、実行中の研究、設定を調べる。
2. 案にIDを付ける。提案AI・モデル・reasoning（分かる範囲）、基準コミット、観測事実、仮説、変更範囲、期待効果、反証条件を保存する。過去レビューを読む前の独立案は上書きしない。
3. 一度に一つの仮説、または分離できない変更群を実装する。複数要因を変えた場合は単独効果と呼ばない。関連する状態遷移・保存・回復のテストと `bun run verify` を通す。
4. **評価前に実装状態をコミットし、実験保存ブランチを作ってpushする。** 作業はmainで行い、保存ブランチは `codex/experiment-<ID>` とする。コミットは「候補の保存」であって採用ではない。対象差分を明示してステージし、秘密・DB・無関係な変更を含めない。
5. 通常API・worker経路で新規live探索を行い、WebUIでレポート・Knowledge・Episode・履歴・使用量を確認する。試行中は対象コードを変更しない。
6. 固定基準で採点し、仮説が予測した行動変化と最終品質を別々に判定する。既存の高得点試行だけを比較相手にせず、採用判断では新規の基準試行も実行する。
7. 改善なら採用記録を保存する。悪化なら、**保存ブランチがリモートに存在することを確認してから**、自分の候補コミットをmain上でrevertし、差し戻しをcommit・pushする。公開履歴をreset・force pushで消さない。複数コミットや他変更が混在する場合は範囲を確認して個別に戻す。
8. 不採用案の説明・評価は `archived/` へ残す。コード保存ブランチは削除しない。基準コミット、実装コミット、保存ブランチ、差し戻しコミット、実行IDを対応付ける。パッチも補助資料として残せるが、唯一のコード保存手段にしない。

この保存手順は、以前の「改善した変更だけをコミットする」を、採用と履歴保全に分けて具体化した運用案である。候補コードも失わず保存し、mainの最終状態は採用済みコードへ戻す。

## 条件と評価

テーマは **PostgreSQL 19 → DeepSeek flash 4.1 → 可逆圧縮 → OpenAI image2.5** を順に入れ替える。名称・版が実在することを前提にしない。同じテーマで基準と候補を比較し、片方だけ違うテーマにしない。

探索モデルはluna/low。各研究の上限は入力1,000,000・出力100,000 tokens、queries 8、rounds 8、documents 16、urls 24、requests 80、wallMs 1200000、depth 4。変更するなら別条件の実験として記録する。

| 評価項目 | 配点 |
| --- | ---: |
| 対象同定と問いへの回答 | 15 |
| 探索・情報増分（費用対情報増分5点を含む） | 25 |
| 根拠・引用・適用条件 | 20 |
| 説明の深さと読みやすさ | 20 |
| Knowledgeの再利用性 | 12 |
| Episodeの正確さ・再利用性 | 8 |

配点を結果を見て変更しない。観点を変更する案は別途示し、過去の点数と直接比較しない。各点に成果物箇所・event/operation IDなどの根拠を付ける。重大な捏造や中心の問いの未回答を文章の流暢さで相殺しない。

初期試行で悪化した候補には次の改修を積み重ねない。1回の差は因果関係の証明ではなく、候補を一旦戻して再設計する判断と区別する。採用候補は4テーマ各2対（基準・候補）、合計16実行（基準8・候補8）で比較する。各テーマの1対目は基準→候補、2対目は候補→基準とし、平均が改善し、各テーマ平均が悪化せず、重大な回帰がないことを確認する。正常完了率も別記する。80点達成は単発の最高点で宣言しない。

主指標は固定評価点。重大な引用誤り・本文消失・正常完了率・実測コストをガードレールとする。費用増加を点数だけで隠さず併記する。基準と候補は同日・近接時間に実行し、取得資料のURL・本文ハッシュ・失敗状況を対ごとに保存する。外部障害で比較不能な対は勝敗から除外して別記し、除外理由を残す。

全呼び出しの入力・出力実測を分けて集計し、試行ごとと実験全体の累積を報告する。キャッシュ・推論tokenを二重加算しない。不明量は不明と記録する。実行時間、partial理由、無効操作数、訂正結果、SystemContext・作業データ・schemaの大きさも保存する。

## 必ず残す証跡

各試行を別ディレクトリへ保存する。`data/evaluations/<実験ID>/<試行ID>/` はgitignore対象なので、他のAIや別端末にも必要な要約と再現手順は追跡対象のdocsにも残す。

- 実装コミット、モデル・reasoning、全予算、SystemContext版、実行ID、開始・終了時刻。
- 生の実行詳細・LLM入出力監査・操作台帳・使用量。秘密情報は保存・公開しない。
- 当時見えていた情報、選択した行動、明示理由、結果、情報増分、選べた代替を時系列で整理した台帳。
- 最終成果物と途中版の比較、引用の支持関係、Knowledge・Episode、採点根拠。
- 観測事実／解釈／原因仮説／未検証、採否、復元方法。

fixtureは制御分岐、保存資料の再生は生成処理、新規Web探索は探索品質の検証である。テスト通過や再生結果をlive品質の証明にしない。LLMの内部思考を推測して原因と断定しない。
