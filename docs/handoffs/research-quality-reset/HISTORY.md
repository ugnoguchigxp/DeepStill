# 過去の分析・改善履歴：独立評価の後に読む

作成日：2026-09-13。START-HERE.mdに従って独立評価を保存した後に参照する。ここにある点数・原因仮説・優先順位は過去の担当の評価であり、新しいセッションの結論を拘束しない。

2026-09-14以降の比較実験、候補コミット、保存ブランチ、revert、最新の採否は [TRIAL-HISTORY.md](TRIAL-HISTORY.md) に集約している。本書はそれ以前の設計変遷と分析上の注意を残す。

## 1. 設計の変遷

当初はMemoryを先に作り、方向評価・概念・レビュー等を含めて探索する設計だった。可逆圧縮調査で大量のトークンに対して読み物が薄いこと、中間出力の価値が低いことをユーザーが指摘した。

その後、新規Web探索はdeliverables-v1に変更。本文を読みながらレポートとKnowledgeを更新し、同じ応答で次のread/fetch/search/finishを選択、最後に調査全体のEpisodeを1件生成する。本文がない行動選択ではdraft:nullを許可し、草稿全文を渡さない経路を設けた。引用・Claim等はプログラムが復元する。

この変更は現在の設計の説明であり、最善の設計であるという証明ではない。全文草稿を毎回更新する方式、最終化の役割、状態の圧縮方法なども再検討できる。

## 2. 過去の分析方法とその弱さ

従来は、実行詳細を取得し、イベントから経路を並べ、operationのLLM出力・purpose・auditを読み、保存された引用と原文を照合し、手動で採点した。その後に失敗箇所のコード・プロンプトを修正し、回帰テストと新規E2Eを行った。

ただし次の弱さがある。

- 終了理由と最終成果物の概観を先に報告し、ユーザーが求める経路分解を後回しにしたことがある。
- 取得障害、入力予算、行動選択の誤りを、単一の問題としてまとめて説明したことがある。
- 同一ソースの続きと、別URLの重複を十分に区別していない説明があった。
- 改修前後で予算、PDF抽出、プロンプト等が変わり、一要因の効果を切り分けにくい。
- 手動採点の配点は共通でも各点の基準が十分に固定されていない。過去点は厳密な実験結果ではない。
- 不適切な行動への注意をプロンプトへ追加する修正が多く、状態表現や更新契約の欠陥が残る。
- 評価者が意図したKV Memの意味を後付けしていないか、確認が必要。

新しいセッションはこの方法そのものを改善してよい。公開された短い判断理由は確認できるが、LLMの非公開の思考過程を分析したと表現してはいけない。

## 4. 実装した主な改善

- 新規Web調査をAPI・worker・通常DB経由で実行し、WebUIに結果と実行履歴を残す。
- HTML本文リンクの候補化、長文の連続カーソル読解、読了済みreadの候補除外。
- 新規本文を与えたときはdraft更新を必須とし、何も読んでいない行動判断ではdraft:nullを許可。
- 行動エラーの修正と成果物修正をrepairKindで分け、行動修正の入力を軽量に保つ。
- 終了再検討にもnavigationの区別を適用。不正行動と予算停止をEpisode向け履歴に含める。
- 読み終わった資料と未取得候補の違い、曖昧語の別候補、README以外の実装・独立資料への遷移を指示へ追加。
- 入力・出力別の予算、実測精算、WebUI表示。内訳不明の予約は保持。
- llm-fetchを0.1.0から0.1.1へ更新。

直前の標準検証は242テスト通過。ただしこれらの機能試験は、探索全体や文章品質の合格を示さない。

## 5. 最新実行から得た原因仮説

以下は次の実装指示ではなく、再確認すべき候補。

| 観測・仮説 | 過去に考えた改修候補 | 再検証する点 |
| --- | --- | --- |
| 新規本文なしの終了時に草稿が16段落2,638文字から8段落1,233文字へ縮んだ | 終了判断と草稿の再生成を分け、根拠のない情報落ちを防ぐ | 冗長な削減と有用情報の消失を分ける。長さ維持だけを合格にしない |
| ガード保留後にLMCache関連が連続した | 由来・同一性を持つ候補管理、早期の別概念・別プロジェクト検索 | 一律のドメイン分散は有益な深掘りを阻害しないか |
| partial PDFから「未読ページがある」と生成した | 抽出不完全・未読本文・未解析図表を状態として分離 | 実際のpageMap、omittedPages、カーソルとLLM入力の対応 |
| 無情報のREADME取得が残った | 既に同一説明を読んだことを明示し、src/test等の目的に合うリンクを選ぶ | README先読みが本当に予測可能か。取得前の情報で判断する |
| 18万予算では正当なreadも予約で停止 | 残入力枠に応じた本文分割、実際のプロバイダー能力と予約の整合 | 今回は予算増額で進めただけ。見積もりの効率化を実証していない |
| Knowledgeが単一論文の結果を一般化し、注意だけのカードも残る | 方式・論文・条件を限定し、再利用単位を再設計 | カード数やフィールドの充足だけで判定しない |

現在のdeliverable-engineには連続8失敗の停止、入力JSON100,000 bytes制限、Episode用22,000トークン留保がある。これらはユーザーの品質要件そのものではない。停止理由と実際の制約が一致しているかも確認する。

## 6. llm-fetchの経緯と依頼書

0.1.0では、通常の技術文書中のmemory/store、token/output等の共起がガード保留につながる最小再現を作成した。0.1.1では無害4例と攻撃4例の最小再現が期待どおりになり、ACL論文PDF等が読めることを確認した。すべてのサイトの問題が解決したわけではない。

既存の正式依頼書と再現コード：

- docs/requests/llm-fetch-guard-false-positives/REQUEST.md
- docs/requests/llm-fetch-guard-false-positives/reproduce.mjs
- docs/requests/llm-fetch-guard-false-positives/baseline-0.1.0.jsonl
- docs/requests/llm-fetch-guard-false-positives.zip
- data/evaluations/llm-fetch-guard/0.1.1/verification.md

最新実行の8件の保留をすべて誤検知と判定したわけではない。ガードdecision、分類、該当範囲、抽出状態を分けて調査する。拒否された内容を別URLへ移すことで回避しない。新しい依頼書は、版、入力fixture、コマンド、期待値・実測、影響、無害例と攻撃例の双方の回帰条件を含める。外部への送信はまだ行っていない。

導入時、Bunの依存解決が停止したためnpm経由で更新し、registry metadataに合わせてbun.lockも更新した。frozen install完了はその時点では未確認。現在の再現性を別途確認する。
