## 1. 依頼内容

通常の技術説明を、モデルへの指示・秘密送信・記憶変更と誤認して取得を止める問題を修正してください。事実説明と外部からの動作要求を区別し、技術文書を読み取り用の根拠として利用できる状態にすることを求めます。

ガードの無効化や拒否結果の一括許可を求める依頼ではありません。直接の指示上書き、秘密送信、永続メモリへの指示、隠し指示などの検出は維持してください。

実装方法は担当者の設計判断に委ねます。以下の再現例、機能要件、回帰条件を満たす変更と、その限界を説明できる検証結果を納品してください。

## 2. 利用側への影響

DeepStillは検索で発見したURLをllm-fetchで取得し、許可された本文から引用付きReportとKnowledgeを作成します。調査全体の経過はEpisodeとして1件にまとめます。外部文書は常にuntrustedとして扱います。

KV Memの通常E2E（job `44099f77-12a7-4db4-9219-116ddf7335d2`）では、検索3回、取得試行8 URLのうち本文として保存できたのはACLの要旨1件でした。他7件は `GUARD_DENIED / require_approval` で保留されました。その結果、アーキテクチャ、計算過程、具体例、KVキャッシュとの比較に必要な根拠が得られず、レポートは要旨由来の3段落に留まりました。

代表的な保留対象はACL論文PDF、KV cacheの技術記事、arXiv論文です。ただし、保留された7資料すべてを無害と判定したわけではありません。本依頼で誤検知と断定する根拠は、次節の人工的な短文による再現結果です。特定ドメインを許可して解決しないでください。

DeepStillのレポート品質には別の実装上の問題もありました。すべての品質問題をllm-fetchに帰属させるものではありません。

## 3. 最小再現と現状

同梱の `reproduce.mjs` は公開APIだけを使う独立した再現スクリプトです。DeepStillのDB、LLM、APIキー、Webサイトへのアクセスは不要です。URLは入力メタデータであり、HTTP取得は行いません。

確認環境: Bun 1.3.14。スクリプトはJavaScriptで、Node.js v24.11.1でも実行し、同じ結果になることを確認済みです。

新しい作業ディレクトリに本書とスクリプトを配置して実行してください。

```sh
npm init -y
npm install --save-exact llm-fetch@0.1.0
bun reproduce.mjs
bun reproduce.mjs --check
```

0.1.0では8件中4件が期待と不一致です。通常実行は診断を出力し、`--check`は不一致がある場合に終了コード1を返します。同梱の `baseline-0.1.0.jsonl` が実測結果です。

全例に共通する設定は `contentType: "text/plain"`、`requestedUse: "extract_facts"`、`source.trust: "untrusted"`。プロファイルは既定値、検査上限は既定値で、切り詰めが原因となる長さではありません。

| ID | 入力 | 実際の検出 | 実際の判定 | 修正後の期待 |
| --- | --- | --- | --- | --- |
| memory-description | Key-value memory networks store representations of documents. | memory_write / high | require_approval | 読み取り可能 |
| separate-facts | The model uses a scoring function.（空行）The experiments run on a public dataset. | tool_invocation / high | require_approval | 読み取り可能 |
| token-description | A token is a unit of text. The model produces output probabilities. | secret_exfiltration / critical | require_approval | 読み取り可能 |
| benign-context | This article describes how key-value memory networks store representations of documents. | memory_write / high、benign_mention / info | require_approval | 読み取り可能 |

ここで「読み取り可能」は `allow` または `allow_with_warning`、かつこれらの無害な記述にhigh/criticalの攻撃検出がない状態を指します。`untrusted`をtrustedへ変更することは求めません。

攻撃側の対照例もスクリプトに含めています。直接の指示上書き、APIキー送信、永続メモリへの指示、無害な前置き付き指示の4例です。現状は4例とも保留されます。修正後も `require_approval` または `deny` を維持してください。8例の通過だけを全体の安全性の証明としないでください。

## 4. 原因として確認した実装

以下の行番号は上記コミットに対するものです。npm 0.1.0の配布ソースマップとも検出条件が一致し、0.1.1準備版での主要な差分は書式変更でした。

- `src/security/rules.ts:224`: `rule.all.every(pattern => pattern.test(variant.text))` により、セグメント全体に複数の語が存在するかを独立に検査する。
- 同ファイルのmemory_write、tool_invocation、secret_exfiltrationルールは、それぞれmemory/store、function/run、token/outputの共起だけでも一致する。
- `findingFor`のbenign判定はconfidenceを下げるがseverityを維持する。
- `src/security/policy.ts:30–50`: benign_mentionを除いた最大severityで保留・拒否を決めるため、benign_mentionを併記しても読み取り可能にはならない。

この組み合わせでは、別々の文の単語が誤って関連付けられます。同じ文にある通常の説明も誤検知するため、文分割だけでは解決しません。反対に、命令を複数文に分割した攻撃もあるため、文境界の外をすべて検査対象外にする修正にも問題があります。

## 5. 改修要件

| ID | 要件 | 確認方法 |
| --- | --- | --- |
| R1 | 単語の共起だけで高重大度の命令と確定しない。動作要求・対象・宛先など、カテゴリごとの関係を確認する | 無害4例と攻撃対照例の比較 |
| R2 | NLPのtokenと認証token等を区別し、通常のoutputの説明を秘密漏洩扱いしない | token説明、認証情報の開示・送信の対照テスト |
| R3 | 文をまたぐ偶然の共起を抑えつつ、複数文に分かれた攻撃の検出を維持する | 文順・空行・長文・命令連鎖のテスト |
| R4 | article、example等の語や引用形式を理由に、文書全体を免除しない | 無害な前置きと実際の攻撃の混在テスト |
| R5 | 可視本文とhidden/comment/template/meta/attributeを区別し、隠し指示や難読化の検査を維持する | 既存コーパスと追加HTMLテスト |
| R6 | どのルール・一致範囲で判定したか追跡可能にする | 診断出力のテスト。秘密や文書全文の無条件ログ出力は避ける |
| R7 | requestedUse、検査上限、切り詰め時の保留・拒否、untrusted属性を維持する | 用途別・上限超過・切り詰めテスト |
| R8 | 公開API・判定値の互換性を保ち、追加フィールド等の変更は明示する | 型・パッケージ検証、移行説明 |

LLM判定器や外部APIの追加を必須とはしません。追加コストや非決定性を伴う方式を採る場合は、その必要性、費用、タイムアウト時の動作を設計説明に含めてください。

## 6. 修正として受け入れない方法

- ガード無効化、`require_approval`の一括許可、severityやconfidenceの閾値を根拠なく一律変更する。
- 論文サイトのドメイン許可リストや、この8例の文字列を特別扱いする。
- hidden等の検査対象や本文を黙って削って「誤検知が減った」とする。
- 文分割または距離制限だけを導入し、分割された攻撃を検証しない。
- 誤検知テストを通すために既存の攻撃テストを削除・弱体化する。

## 7. 受け入れ試験

| ID | 試験 | 合格条件 |
| --- | --- | --- |
| A1 | 同梱再現スクリプトを修正版に対して `--check` で実行 | 8件中不一致0、終了コード0 |
| A2 | 既存の攻撃コーパスを同条件で修正前後比較 | 既存の保留・拒否ケースが読み取り可能へ変化しない。差分一覧を添付 |
| A3 | 英語・日本語の通常技術説明、命令、混在文を追加 | 期待判定と実際の判定が一致。件数とカテゴリ別結果を添付 |
| A4 | text/plain、HTML可視文、隠し文、属性、難読化、PDF抽出相当の改行入りテキスト | 検出するべき指示を維持し、通常説明を拒否しない |
| A5 | 文境界、空行、語順、長文中の離れた語、複数文の攻撃、検査上限超過 | R3・R7を満たす。単に見なくなった結果の通過ではない |
| A6 | llm-fetchの標準検証 | lint・型・単体テスト・coverage・ガードコーパス・配布パッケージ検証が成功 |
| A7 | 性能比較 | 同じ入力・上限・環境で修正前後の時間を提示。大きな悪化がある場合は理由と対処を記載 |

既存攻撃ケースの期待判定そのものが誤っていると考えられる場合は、別途、個別の根拠と期待値変更を明示してください。黙って期待値を変えてA2を通過させないでください。

## 8. 納品物と担当の分担

llm-fetch担当に依頼する納品物:

1. 原因と設計判断を説明した修正PR。変更したルール、変更しなかった保護、残る検出限界を明記する。
2. 最小再現を含む回帰テストと、修正前後のコーパス比較結果。
3. A1〜A7の実行コマンド、使用コミット、結果。未実施項目は理由を記載する。
4. 利用側が固定できる修正版番号、または公開前検証用の固定コミットとパッケージ。リリースノートに判定挙動の変更を記載する。

DeepStill側で引き受ける作業:

1. 修正版を固定バージョンで導入し、lockfileと抽出器バージョンの記録を更新する。
2. 同梱再現、既存のcrawler・引用・探索テスト、標準検証を実行する。
3. 保存資料の再生ではなく、新しいKV Mem通常E2Eを実行する。
4. 検索→取得→読解→追加探索→レポートの経路を分解し、引用・具体例・比較・Knowledge・調査全体1件のEpisodeを確認する。
5. 探索とレポートの総合評価が80点を超えるまで、残るDeepStill側の問題を改善する。LocalLLMの実測は行わない。

llm-fetchの修正受け入れと、DeepStill全体の80点超えは別の判定です。レポート品質の責任をすべてライブラリ側に移しません。

## 9. 推奨する進め方

上流のガード実装を修正し、正規のバージョン更新としてDeepStillへ取り込むことを推奨します。利用側で拒否結果を上書きすると、検出の責任範囲が二重になり、更新時にも修正の有無を追えなくなるためです。

公開待ちが長い場合に限り、同じ修正とテストを含む固定コミットのパッケージでDeepStillの統合検証を先行します。npm公開は本依頼書による実行指示ではなく、メンテナの通常のリリース手順に従ってください。

着手時には修正範囲と検証計画、提出時にはA1〜A7の結果と導入方法をご提示ください。希望納期は未設定です。
